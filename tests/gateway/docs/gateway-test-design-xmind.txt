AIDP Gateway独立测试设计
	测试设计输入：设计/开发人员/TSE串讲/交流过程
		需求背景
			分析思路
				1、客户场景分析：Gateway作为AIDP业务统一入口，需要在标准K8s集群上独立部署并完成基础路由、策略绑定、跨命名空间引用控制和业务IP对外暴露。
				2、局点信息分析：客户希望Gateway可以独立于IAM验证，先证明网关入口、路由转发、网络前端业务IP、异常恢复能力可靠。
				3、本测试方案仅覆盖Gateway两类对象：GW路由初始化类、BIP业务IP类；IAM认证、ACL、API Key等不纳入本方案。
			分析结果
				Gateway独立测试拆分为两组：
					GW：应用初始化与路由集成
					BIP：业务IP配置与容器网络前端集成
				测试后端采用whoami或任意HTTP echo服务，作为Gateway转发链路验证对象。
				BIP依赖平台DM和容器网络前端能力，平台内部实现不展开，只验证Gateway集成结果。
		友商竞争力分析
			分析思路
				1、对标主流K8s Gateway/Ingress能力：支持声明式路由、跨namespace授权、策略绑定、滚动升级、入口IP暴露。
				2、差异点：本方案额外关注平台前端网络平面分配业务IP、StatefulSet保IP、节点漂移保IP。
				3、竞争力验证重点不做友商实测，聚焦客户黑盒可感知能力。
			分析结果
				不展开友商实测。
				形成黑盒验收点：一键部署可用、路由可达、未授权不转发、业务IP稳定、故障后可恢复。
		NAS协议一致性分析
			分析思路
				1、本特性为K8s Gateway与容器网络前端集成，不涉及NFS/SMB协议一致性。
				2、不涉及新增NAS报文字段、NAS命令字、主机侧NAS协议行为。
			分析结果
				不涉及NAS协议一致性测试。
		周边依赖对象分析
			分析思路
				1、外部依赖：K8s API Server、Helm、Envoy Gateway Controller、Gateway API CRD、容器网络插件、DM前端网络平面。
				2、内部依赖：GatewayClass、Gateway、EnvoyProxy、HTTPRoute、ReferenceGrant、SecurityPolicy、BackendTrafficPolicy、ClientTrafficPolicy。
				3、兼容性依赖：K8s版本、Gateway API版本、Envoy Gateway版本、NodePort/LoadBalancer/业务IP暴露方式。
			分析结果
				GW测试关注K8s资源状态和HTTP访问结果。
				BIP测试关注Pod注解、业务IP绑定、Pod重建、网络平面变更和节点漂移后的业务可达。
		关键NAS测试对象分析
			测试因子提取
				分析思路
					被测对象
						Gateway控制面：Envoy Gateway Controller
						Gateway数据面：Envoy data-plane Pod/Service
						Gateway API资源：GatewayClass、Gateway、HTTPRoute、ReferenceGrant
						策略资源：SecurityPolicy、BackendTrafficPolicy、ClientTrafficPolicy
						业务IP资源：前端网络平面、Pod网络注解、业务IP绑定关系
					外部依赖
						环境组网
							NodePort入口
							LoadBalancer入口
							平台业务IP入口
						测试后端
							whoami Deployment
							whoami Service
					内部依赖
						Gateway reconcile流程
						Envoy配置下发流程
						HTTPRoute状态更新流程
						策略绑定与生效流程
					模块内部流程处理
						一键部署流程
						重复部署幂等流程
						路由创建生效流程
						跨命名空间引用授权流程
						默认拒绝流程
						业务IP分配和恢复流程
				分析结果
					测试因子：
						部署方式：首次安装、重复安装、升级
						路由类型：有效路由、无路由、路径不匹配路由
						后端引用：同namespace、跨namespace有ReferenceGrant、跨namespace无ReferenceGrant
						来源IP：白名单来源、非白名单来源、SNAT场景
						路径白名单：允许路径、未配置路径
						业务IP：首次分配、Pod重建保IP、变更网络平面换IP、节点故障漂移保IP
			规格资源项分析
				分析思路
					外部规格（客户面可见）
						Gateway副本数
						Gateway暴露端口
						NodePort端口
						业务IP数量
						HTTPRoute数量
						ReferenceGrant数量
					内部规格（流程相关，客户不可见）
						Controller reconcile延迟
						Envoy配置下发延迟
						策略生效延迟
					超规格
						IP池耗尽
						不存在的网络平面
						非法部署参数
					资源访问互斥能力
						升级和流量访问并发
						Pod重建和业务访问并发
						节点漂移和业务访问并发
				分析结果
					本轮主测SR验收，不展开大规格压力。
					保留IP池耗尽、非法网络平面为后续异常扩展用例。
			缓存专项分析
				分析思路
					本特性不直接新增业务缓存。
					Gateway配置缓存属于Envoy/Gateway Controller内部能力，黑盒仅观察配置生效和恢复。
				分析结果
					不单独设计缓存专项。
			关键流程分析
				分析思路
					模块内部时序图
						管理员执行helm安装 -> CRD创建 -> controller启动 -> GatewayClass/Gateway创建 -> Envoy data-plane启动 -> Service暴露 -> 外部访问
						创建HTTPRoute -> Gateway Controller reconcile -> Envoy配置更新 -> 外部请求转发后端
						跨namespace HTTPRoute引用Service -> 检查ReferenceGrant -> 有授权放行 -> 无授权拒绝
						指定前端网络平面 -> Pod注解生效 -> 平台分配业务IP -> 外部访问业务IP
						Pod重建/节点故障 -> 平台按稳定身份恢复业务IP -> Gateway恢复可达
					MST测试覆盖
						模块功能
							对外提供的接口
								K8s API资源接口
								HTTP外部访问入口
							需要调用的接口
								K8s API Server
								容器网络前端接口
								DM网络平面配置
							模块流程
								主流程：部署、路由、业务IP可达
								异常分支：无ReferenceGrant、非白名单IP、未配置路径、Pod重建、节点漂移
						模块可靠性
							Pod重建
							节点故障漂移
							滚动升级
							策略恢复
				分析结果
					关键流程通过黑盒用例覆盖，必要时补充kubectl状态、日志和事件作为观察点。
			后台任务
				分析思路
					不涉及业务后台任务。
					Gateway Controller reconcile可视为控制面后台调谐流程。
				分析结果
					通过资源状态、事件和访问结果观察reconcile是否生效。
			引用计数
				分析思路
					不涉及显式引用计数。
				分析结果
					不设计引用计数专项。
			故障模式
				分析思路
					新增或相关故障模式：
						Gateway controller异常
						Envoy data-plane Pod异常
						ReferenceGrant缺失
						策略配置错误
						业务IP分配失败
						节点故障导致Pod迁移
				分析结果
					本轮覆盖Pod异常重建、节点故障漂移、未授权不转发。
			数据可靠性
				分析思路
					Gateway不持久化业务数据。
					关注配置幂等和升级不破坏已有路由。
				分析结果
					通过重复部署、滚动升级、路由继续可用验证配置可靠性。
			升级影响性
				1、该特性影响Gateway滚动升级流程。
				2、需要验证升级期间路由不中断、变更网络平面后新业务IP生效。
				分析结果
					GW覆盖幂等部署。
					BIP覆盖变更网络平面滚动升级。
			是否涉及硬件形态
				分析思路
					SR支持产品为A800。
					Gateway本身主要依赖K8s与容器网络能力，不直接依赖专用硬件板卡。
				分析结果
					本轮按A800标准K8s环境验证。
			通用观察项
				分析思路
					黑盒观察项
						HTTP状态码
						whoami返回内容
						后端访问日志
						Gateway/HTTPRoute状态
						Pod Ready状态
						业务IP绑定关系
					内部观察项
						kubectl describe事件
						controller日志
						data-plane日志
						平台DM网络平面页面
				分析结果
					每个拒绝类用例必须同时检查HTTP返回码和后端日志，证明请求未到达后端。
		可测试性需求分析
			原则
				基于关键测试对象和流程可操作、可构造、可观察原则，识别测试手段。
			可测试性需求
				需要提供Gateway一键部署命令。
				需要提供whoami或等价HTTP echo后端。
				需要提供查询Gateway/HTTPRoute状态的kubectl命令。
				需要提供查询业务IP绑定关系的命令或DM页面路径。
				需要提供Pod重建和节点漂移的可控触发方式。
				需要提供保源IP方案，否则IP白名单只能做配置验证，无法做真实来源IP拦截验证。
		约束限制分析
			分析思路
				业务IP测试依赖平台网络前端能力，不是纯标准K8s即可完成。
				IP白名单依赖Gateway能够识别真实源IP，NodePort/LoadBalancer如果SNAT会影响测试结论。
				节点故障漂移测试涉及集群变更，需在可演练环境执行。
			分析结果
				BIP用例标记为平台集成用例。
				节点故障优先使用cordon/drain模拟，避免破坏性操作。
		等价类分析规则
			分析思路
				按测试对象划分等价类，避免无意义组合爆炸。
			分析结果
				部署等价类：首次部署、重复部署、滚动升级。
				路由等价类：匹配路径、不匹配路径、跨namespace引用。
				授权等价类：有ReferenceGrant、无ReferenceGrant。
				来源IP等价类：白名单来源、非白名单来源。
				业务IP等价类：首次分配、重建恢复、网络平面变更、节点漂移。
