# AI 友好型软件工程固化流程

本文是对 `引用材料/ai-dev-workflow.md` 的比赛化整理版，也是本次作品中“固化流程”的详细说明。它回答三个问题：

1. 什么叫 AI 友好型软件工程。
2. 白+黑模式为什么可以连续跑一晚上。
3. 这套流程如何覆盖新项目开发、新增需求、Bug 修复和自动运维。

## 1. 核心定义

AI 友好型软件工程不是简单地“多用 AI 写代码”，而是把软件工程的输入、约束、测试、反馈和经验都整理成 AI 可读取、可验证、可继承的资产。

传统流程中，很多信息存在人的脑子里：

- 这个接口为什么这么设计。
- 哪些方案已经被否定。
- 哪些测试是上线前必须跑的。
- 某个报错以前是怎么定位的。
- 哪些文件不能随便改。

AI 如果拿不到这些上下文，就会出现“看起来很努力，但理解不准确”的问题。本项目的做法是把这些隐性知识固化为工程资产，让 AI 在工程边界内工作。

```text
AI 友好型软件工程 =
  结构化需求
  + 可执行测试
  + 版本化架构文档
  + 明确代码边界
  + 问题日志
  + 长短期记忆
  + 自动化验证脚本
```

## 3. 标准流程总览

```text
输入：需求 / Bug / 测试任务 / 运维任务
  ↓
上下文加载：项目约束 + 架构 + Story + 测试 + 当前 issue
  ↓
任务分类：新项目 / 新需求 / Bug 修复 / 自动运维
  ↓
测试即规约：先定义验收标准、失败路径和依赖故障场景
  ↓
AI 实现：代码、配置、脚本、文档同步更新
  ↓
自动验证：单测、集成、黑盒、部署、重装
  ↓
人工验收：确认业务语义和体验是否正确
  ↓
记忆沉淀：长期文档、Prompt、Skills、问题清单
```

## 4. 新项目开发流程

新项目或大模块开发使用六阶段流程。

### 4.1 Phase 1：需求结构化

AI 不直接写方案，而是先追问：

1. 隔离粒度是什么。
2. 鉴权发生在哪一层。
3. 数据是静态配置、动态授权还是混合。
4. 依赖服务有哪些，失败时如何处理。
5. 性能基线、数据规模和安全边界是什么。

输出物：

- 结构化功能点。
- 隐含约束列表。
- 验收标准。
- 被否定方案和原因。

### 4.2 Phase 2：架构与接口规约

AI 输出：

- 分层架构图。
- 请求流和失败流。
- 数据库表结构。
- API 规范。
- 跨系统契约。

人工负责拍板：

- 组件边界。
- 数据隔离策略。
- 接口是否锁定。
- 安全默认行为。

### 4.3 Phase 3：测试即规约

代码实现前先生成测试规约：

| 测试类型 | 目标 |
| --- | --- |
| 正常流程 | 功能是否可用 |
| 异常流程 | 输入错误、无权限、越界、跨租户时是否拒绝 |
| 依赖故障 | Keycloak、OPA、DB、Gateway 等异常是否 fail-close |
| 性能基线 | 热路径是否满足基本延迟和吞吐要求 |
| 安全负向 | 是否存在绕权、明文泄露、路径绕过 |

### 4.4 Phase 4：分模块实现

按依赖顺序实现，不一次性铺开：

```text
DB schema
  -> 核心服务逻辑
  -> 鉴权热路径
  -> Gateway / Helm 配置
  -> 测试脚本
  -> 文档同步
```

每个模块完成后立即验证，避免错误堆积。

### 4.5 Phase 5：部署验证

验证不是只跑单测，而是包括：

- clean install。
- 核心鉴权用例。
- Gateway 黑盒访问。
- uninstall cleanup。
- reinstall。
- 再次完整测试。

### 4.6 Phase 6：白+黑验收

当核心路径已经可跑通、集成测试通过率较高时，进入白+黑模式。该阶段目标不是补大功能，而是消化真实问题。

## 5. 新增需求流程

新增需求是最常见的迭代方式。标准执行顺序如下：

```text
需求描述
  -> AI 追问隐含约束
  -> 形成 Story / Spec
  -> 生成测试规约
  -> 补失败测试或验收用例
  -> 实现代码
  -> 运行测试
  -> 更新文档和记忆
```

### 示例：新增 API Key 统一认证

需求：

> 支持外部应用通过 API Key 调用业务接口。

AI 必须先澄清：

- API Key 是否属于租户。
- 是否支持禁用、过期、轮换。
- 是否限制 allowed_paths。
- 是否继续走 OPA 和 resource_acl。
- 明文是否落库。

测试先行：

| 测试 | 预期 |
| --- | --- |
| enabled API Key 访问 allowed path | 进入 OPA 和 ACL |
| disabled API Key | 401 |
| expired API Key | 401 |
| path 不在 allowed_paths | 403 |
| 轮换后旧 Key | 401 |

实现时 AI 只围绕这些测试目标修改代码，不自行增加旁路授权。

## 6. Bug 修复流程

Bug 修复必须遵循“先复现、后修复、再沉淀”。

```text
完整问题记录
  -> 复现用例
  -> 根因分析
  -> 影响范围评估
  -> 最小修复
  -> 回归测试
  -> 更新 issue 状态
  -> 经验沉淀
```

### 标准问题记录

```markdown
### P1 问题标题
- 现象：操作步骤 -> 实际结果 vs 预期结果
- 环境：版本、账号、数据状态
- 复现率：必现 / 偶现
- 日志：错误响应、服务日志、测试输出
- 验收：修复后应满足什么行为
```

### 根因分析协议

AI 修复前必须回答：

1. 是哪个组件返回了错误。
2. 请求是否经过 Gateway 和 ext_authz。
3. 身份解析是否正确。
4. OPA input 和 path_rules 是否正确。
5. resource_acl 查询是否正确。
6. DB 初始化或存量数据是否漂移。
7. 修改是否影响其他路径。

这种协议能避免 AI 看到表面报错就修改局部判断。

## 7. 自动运维流程

自动运维承接开发后期和交付前稳定化。

```text
定时触发 / 人工触发
  -> 部署或重建
  -> 健康检查
  -> 自动化测试
  -> 日志收集
  -> AI 归因
  -> 低风险修复或修复建议
  -> 生成报告
```

### 自动运维能做什么

| 能力 | 说明 |
| --- | --- |
| 环境重建 | 执行 setup / cleanup / reinstall 流程 |
| 测试执行 | 运行鉴权、Gateway、API Key、OPA 测试 |
| 日志归因 | 根据失败日志判断是配置、代码、数据还是环境问题 |
| 回归报告 | 输出失败用例、影响范围、修复建议 |
| 待办生成 | 将不能自动解决的问题写入次日人工确认清单 |

### 自动运维不能做什么

1. 不直接操作生产环境。
2. 不直接执行破坏性数据库变更。
3. 不绕过安全审批。
4. 不替人工决定高风险安全策略。
5. 不把敏感日志写入提交材料。

## 8. 白+黑模式为什么能跑一晚上

白+黑模式能跑一晚上，关键不是“AI 很强”，而是输入和边界足够清楚，让 AI 不需要反复问人。

### 8.1 必要条件

| 条件 | 说明 |
| --- | --- |
| issue 足够结构化 | 每条 issue 有步骤、环境、预期、复现率、优先级 |
| 验证命令明确 | AI 知道修复后运行哪些测试 |
| 修改边界明确 | 不引入新功能、不改接口签名、不顺带重构 |
| 停止条件明确 | 测试通过、无法复现、设计问题、环境问题 |
| 工作区独立 | 夜间运行在独立分支或工作区，避免污染白天环境 |
| 自动化脚本可用 | setup、test、cleanup 等命令可无人工交互执行 |

### 8.2 Todo List 颗粒度

Todo list 要细到 AI 可以独立执行。建议每条 issue 写成：

```markdown
### P1-001 创建资源后创建者无法访问详情

状态：待处理
复现步骤：
1. 使用普通用户 alice 登录
2. 创建 KnowledgeBase 资源 kb-001
3. 立即访问 kb-001 详情

实际结果：403
预期结果：alice 拥有 kb-001 Owner 权限，可访问详情
复现率：必现
相关模块：resource-sync、resource_acl、pep-proxy
验证命令：bash ../代码/deploy/scripts/test.sh
限制：
- 不改 URL 规范
- 不改角色矩阵
- 不引入新功能
完成标准：
- 新增或更新回归测试
- 测试通过
- issue 状态更新为已修复或待确认
```

这样的 Todo list 让 AI 有明确输入、明确边界、明确验收标准，所以可以批量处理。

### 8.3 夜间执行循环

```text
读取 issue 列表
  -> 按 P0 / P1 / P2 排序
  -> 取第一条未处理 issue
  -> 尝试复现
  -> 判断类型：代码 / 配置 / 设计 / 环境
  -> 根因分析
  -> 最小修复
  -> 运行对应测试
  -> 更新 issue 状态
  -> 继续下一条
```

### 8.4 分支与风险控制

夜间修复建议运行在独立分支或工作区：

- `nightly/YYYYMMDD-fix-issues`
- 每修复一组同根因问题形成一个 commit 或补丁。
- P0/P1 优先，P2 只在时间充足时处理。
- 遇到设计问题不硬改，标记为“待人工决策”。
- 遇到环境问题不反复尝试，记录环境证据。

### 8.5 什么情况下 AI 应停止

AI 不能无限循环。遇到以下情况停止当前 issue：

1. 复现条件缺失。
2. 修改需要产品或架构决策。
3. 需要生产权限或敏感凭据。
4. 连续两次修复后同一测试仍失败。
5. 影响范围超过当前 issue 边界。

停止不是失败，而是防止 AI 在信息不足时扩大修改范围。

## 9. 人力节省测算口径

### 9.1 当前项目规模

按当前仓库物理行数统计，排除 `.git`、`artifacts`、`node_modules`、`dist`、`target` 等目录后：

| 范围 | 文件数 | 行数 | 说明 |
| --- | ---: | ---: | --- |
| 核心应用代码 `apps/` | 93 | 26,623 | IAM API、pep-proxy、bundle-server、resource-sync、gateway-manager、Keycloak 扩展等 |
| 部署与测试 `deploy/` | 104 | 38,754 | Helm、脚本、测试入口、Gateway/IAM 部署配置 |
| 构建脚本 `build/` | 4 | 1,061 | Docker / openEuler 构建相关 |
| 测试资产 `tests/` | 17 | 2,624 | e2e、fixtures、手工用例 |
| 工具 `tools/` | 6 | 2,113 | Gateway 接入生成器、API spec 工具等 |
| 活跃工程资产合计 | 224 | 71,175 | 不含 docs 和 legacy |
| 含文档、配置和历史材料的仓库资产 | 328 | 93,558 | 包含 docs、README、部分 legacy |

提交材料中建议使用更稳妥表述：

> 本项目核心应用约 2.7 万行，活跃工程资产约 7.1 万行，含文档和配置约 9.3 万行。

### 9.2 传统人力估算

若完全按传统方式开发，保守估算如下：

| 阶段 | 传统投入 |
| --- | ---: |
| 需求澄清、架构设计、权限模型评审 | 5-8 人日 |
| IAM API、pep-proxy、bundle-server、resource-sync 等核心编码 | 20-30 人日 |
| Helm、镜像、Kind、本地部署和重装验证 | 8-12 人日 |
| JWT、API Key、OPA、ACL、Gateway 全链路联调 | 8-12 人日 |
| DT / 黑盒 / 依赖故障测试设计与补充 | 6-10 人日 |
| 文档、接入指南、交互记录、发布材料 | 5-8 人日 |
| 问题修复、回归、白盒和黑盒验收 | 8-15 人日 |
| 合计 | 60-95 人日 |

如果按 2-3 人团队并行，传统周期约为 4-8 周。

### 9.3 AI 辅助开发投入

本项目通过 AI 参与需求、代码、测试、部署、修复和文档，实际可按以下口径表达：

| 阶段 | AI 辅助后投入 |
| --- | ---: |
| 需求和架构收敛 | 1-2 人日 |
| 核心代码生成与人工评审 | 8-12 人日 |
| 部署脚本、Helm、测试脚本生成与调试 | 4-6 人日 |
| DT / 黑盒 / 依赖故障用例生成 | 1-2 人日 |
| Bug 修复和白+黑验收 | 4-8 人日 |
| 文档和比赛材料整理 | 2-4 人日 |
| 合计 | 20-34 人日 |

按该口径，AI 辅助后整体节省约 40-61 人日，节省比例约 55%-65%。如果按 2-3 人团队计算，周期从 4-8 周压缩到约 1.5-3 周。

### 9.4 为什么这个测算合理

节省主要来自四类工作：

1. **重复编码**：CRUD、DTO、路由、Helm、测试脚本由 AI 快速生成。
2. **测试生成**：依赖故障和权限组合由 AI 系统枚举，减少人工设计时间。
3. **根因分析**：AI 沿跨组件链路排查，减少多人会议式定位。
4. **文档同步**：每次变更同步更新 Story、架构、交互记录和说明书。

不夸大 AI 的部分：

- 架构决策仍由人工拍板。
- 权限语义仍由人工确认。
- 高风险部署和生产变更仍由人工审批。
- AI 生成代码必须通过测试和 review。

## 10. 黄区迁移流程

黄区迁移不是复制蓝区代码，而是复制流程。

```text
蓝区 AIDP IAM 验证
  -> 抽象 Prompt、Skills、测试规范、issue 模板
  -> 脱敏和安全审查
  -> 黄区三助手落地
```

| 蓝区流程能力 | 黄区承接 | 说明 |
| --- | --- | --- |
| 测试即规约 | IT 助手 | 黄区 UT、覆盖率、编译运行闭环 |
| 上下文工程 | 产研助手 | 长短期记忆、知识溯源、DTS 草稿 |
| 自动运维 | 运维助手 | SSH 采集、LLM 推理、诊断报告 |
| 白+黑 | 三助手协同 | 白天收集问题，夜间自动分析和生成修复建议 |

## 11. 摘要表述

> 我们固化的不是一个提示词，而是一条 AI 可执行的软件工程流水线：需求先结构化，测试先规约，代码按上下文生成，问题按 Todo 夜间消化，经验再沉淀为长期记忆，因此它可以从蓝区 IAM 复杂工程复制到黄区研发、测试和运维场景。
