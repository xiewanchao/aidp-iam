# 创新点：白加黑协作模式

> 一句话定位：白天由人发现真实问题，夜间由 AI 批量消化结构化 issue，形成“人工探索 + AI 系统修复”的日循环。

## TRIGGER：什么时候进入白加黑

不是项目一开始就进入白加黑。必须满足以下条件：

| 条件 | 说明 |
| --- | --- |
| 核心路径可跑通 | 系统已具备可测试的完整链路 |
| 集成测试通过率较高 | 问题已从“功能缺失”转为“行为偏差” |
| 部署脚本可重复执行 | 夜间可以独立重建和验证 |
| issue 可结构化记录 | 白天能提供步骤、环境、预期和复现率 |
| AI 修改边界明确 | 夜间不引入新功能，不改接口签名 |

不满足这些条件时，夜间 AI 会花大量时间补基础功能或猜问题，不适合跑整晚。

## WHY：为什么白加黑有效

人工和 AI 的优势不同：

| 任务 | 人更擅长 | AI 更擅长 |
| --- | --- | --- |
| 发现问题 | 真实业务直觉、体验判断、设计取舍 | 系统枚举、重复执行 |
| 定位问题 | 决定是否符合业务预期 | 沿调用链查日志和代码 |
| 修复问题 | 决定是否改变设计 | 跨文件一致性修改 |
| 回归验证 | 判断结果是否符合用户体验 | 自动运行测试和生成报告 |

所以白加黑不是把 AI 当夜间劳动力，而是把工作切成两类：

- 白天：人做探索和判断。
- 夜间：AI 做批量分析、修复和回归。

## CONTEXT LOADING：夜间任务需要什么输入

| 输入 | 要求 |
| --- | --- |
| issue 列表 | P0/P1/P2 分类，步骤清楚 |
| 验证命令 | 每条 issue 对应测试命令或验收方式 |
| 修改边界 | 禁止改接口、禁止新功能、禁止顺带重构 |
| 架构文档 | 方便 AI 沿调用链定位 |
| 历史陷阱 | 防止重复走错方向 |
| 停止条件 | 设计问题、环境问题、权限不足时停止 |

## WORKFLOW：夜间 AI 执行流程

```text
读取 issue 列表
  -> 按 P0 / P1 / P2 排序
  -> 选择第一条待处理 issue
  -> 复现或静态确认
  -> 分类：代码 / 配置 / 设计 / 环境
  -> 根因分析
  -> 最小修复
  -> 运行测试
  -> 更新 issue 状态
  -> 输出摘要
  -> 继续下一条
```

## 为什么可以跑一晚上

### 1. Todo 足够细

AI 能持续工作，是因为每个任务已经被拆成可执行单元：

- 现象明确。
- 预期明确。
- 边界明确。
- 验证明确。

只要 Todo 颗粒度足够细，AI 不需要等人回答“下一步做什么”。

### 2. 自动化验证可重复

夜间任务需要有可重复命令：

```text
../代码/deploy/scripts/test.sh
../代码/deploy/scripts/test-gateway.sh
../代码/deploy/scripts/test-apikey.sh
../代码/deploy/scripts/test-opa.sh
```

AI 修复后可以自己运行相关验证，再决定是否继续。

### 3. 有明确停止条件

AI 不能无限尝试。以下情况必须停止当前 issue：

| 停止原因 | 处理 |
| --- | --- |
| 缺少复现条件 | 标记为待补充信息 |
| 涉及设计决策 | 标记为待人工决策 |
| 需要敏感权限 | 标记为需要人工操作 |
| 连续两次修复失败 | 输出已排除原因和建议 |
| 影响范围扩大 | 停止，要求人工确认 |

### 4. 独立分支降低风险

夜间修复建议使用独立分支：

```text
nightly/YYYYMMDD-issues
```

每个同根因问题形成一组补丁，次日人工 review 后再合入。

## PROMPT TEMPLATES

### 夜间启动

```text
读取今天的 issue 列表。
按 P0 -> P1 -> P2 处理。
每条 issue 必须先复现或确认触发条件，再做根因分析。
修复时不引入新功能、不改接口签名、不顺带重构。
修复后运行对应验证命令，并更新 issue 状态。
```


## METRICS：衡量指标

| 指标 | 说明 |
| --- | --- |
| 夜间 issue 消化率 | 夜间处理 issue 数 / 白天新增 issue 数 |
| P0 清零时间 | 阻断问题从记录到修复的时间 |
| 待人工决策比例 | 反映 issue 是否拆得足够清楚 |
| 回归测试补充率 | 修复后是否沉淀测试 |
| 二次打开率 | 已修复问题是否复发 |

## AIDP IAM 示例

### 示例：创建资源后访问失败

白天记录：

```text
普通用户创建资源后立即访问详情返回 403。
预期创建者应拥有 Owner 权限。
```

夜间 AI 处理：

1. 判断可能涉及 resource-sync。
2. 检查创建响应是否被 ext_proc 捕获。
3. 检查资源 ID 提取规则。
4. 检查 Owner ACL 是否写入。
5. 检查 pep-proxy 查询是否命中 ACL。
6. 修复配置或提取逻辑。
7. 补充回归测试。

次日人工：

- 使用普通用户重新创建资源。
- 验证详情访问、分享、删除按钮权限。
