# 效率收益与人力节省测算

> 一句话定位：用代码规模、阶段投入和场景提效说明 AI 流程到底节省了多少人力。

## 1. 测算口径

本测算基于当前仓库物理行数和实践过程观察，排除 `.git`、`artifacts`、`node_modules`、`dist`、`target` 等生成或缓存目录。

提交材料中建议使用“保守估算”表述，并说明：

1. 行数是当前仓库统计口径。
2. 人力是按复杂后端/K8s/IAM 工程经验估算。
3. AI 并未替代全部人工，架构、安全和验收仍由人工把关。

| 合计 |  | 60-95 人日 |

按 2-3 人团队并行，传统周期约 4-8 周。

## 6. 节省来自哪里

### 6.1 重复编码

AI 适合生成：

- CRUD。
- DTO / Pydantic Model。
- TypeScript 类型。
- Helm 模板。
- 测试脚本骨架。
- API 文档。

人工保留：

- 架构边界。
- 权限语义。
- 安全策略。
- 最终验收。

### 6.2 测试生成

人工容易遗漏依赖故障，AI 可以系统枚举：

- Keycloak 故障。
- OPA 不可用。
- DB 超时。
- API Key 过期。
- 跨租户拒绝。
- ACL 不足。

### 6.3 根因分析

传统排查需要多人一起看 Gateway、OPA、DB、服务日志。AI 可以按协议追踪：

```text
HTTP 现象 -> Gateway -> pep-proxy -> OPA -> DB -> resource_acl -> 初始化数据
```

### 6.4 文档同步

AI 能在代码变更后同步：

- 架构文档。
- Story。
- API 说明。
- 测试说明。
- 交互记录。

## 7. 白加黑带来的额外收益

白天人工只记录，不临时修补。夜间 AI 统一处理。

收益：

1. 减少白天上下文切换。
2. 减少临时补丁带来的返工。
3. 夜间批量处理同根因问题。
4. 次日有明确验收清单。
5. 每个修复都能补回归测试。

## 8. 黄区助手收益口径

| 助手 | 可量化指标 |
| --- | --- |
| IT 助手 | 覆盖率提升、UT 用例数、编译通过率、单文件补测耗时 |
| 产研助手 | 文档核对耗时、DTS 草稿生成数、知识卡片数、问答溯源率 |
| 运维助手 | 诊断耗时、采集主机数、报告生成时间、问题定界准确率 |

## 9. 风险和保守说明

为了避免口径夸大，建议明确说明：

1. AI 不能替代安全评审。
2. AI 不能替代业务价值判断。
3. AI 不能无审批操作生产。
4. AI 生成代码必须通过测试和 review。
5. 人力节省是按当前项目实践估算，最终可按团队真实工时校准。

## 10. 摘要口径

> 这个项目不是几百行 Demo，而是核心应用约 2.7 万行、活跃工程资产约 7.1 万行的复杂工程。传统开发保守需要 60-95 人日，我们通过上下文工程、测试即规约、AI 代码生成、白+黑修复和自动运维，把投入压缩到约 23-39 人日，节省约 50%-60%。更重要的是，这些能力已经沉淀为可复制流程，可以迁移到黄区 IT、产研和运维助手。
