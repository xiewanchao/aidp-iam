# AI 编程实践流程：蓝区验证到黄区迁移

本文用于说明实践流程如何从“整个项目开发”扩展到“新增需求、Bug 修复、自动运维”，并解释为什么测试应前置到实现之前。

## 1. 总体流程

```text
Phase 0 任务识别
  -> 新项目 / 新需求 / Bug 修复 / 测试补充 / 自动运维

Phase 1 上下文加载
  -> 项目约束、架构文档、测试规约、短期 issue、长期记忆

Phase 2 Spec 与测试规约
  -> 结构化需求、接口契约、验收标准、失败路径、依赖故障用例

Phase 3 实现与修改
  -> AI 在 Spec 和测试约束下生成代码、配置、脚本

Phase 4 自动化验证
  -> 单测、集成、黑盒、部署、清理重装

Phase 5 白+黑验收
  -> 白天人工探索，夜间 AI 修复和补回归

Phase 6 记忆沉淀与黄区迁移
  -> Prompt / Skills / 测试模板 / issue 模板 / 助手流程
```

## 2. 为什么测试要放到实现前面

在 AI 编程中，测试前置比传统 TDD 更重要，原因是 AI 最容易出错的地方不是语法，而是“理解错了要实现什么”。

测试前置解决三个问题：

1. **需求对齐**：先把“什么叫做成功”写清楚，AI 实现时有明确目标。
2. **边界显式化**：异常操作、依赖故障、跨租户、无权限等容易遗漏的路径先被列出。
3. **防止表面修复**：Bug 修复先有失败用例，AI 必须让用例通过，而不是只消除报错。

调整后的开发顺序：

```text
旧流程：需求 -> AI 实现 -> 测试 -> 发现偏差 -> 返工

新流程：需求 -> Spec -> 测试规约 -> AI 实现 -> 自动验证 -> 记忆沉淀
```

不是所有测试都必须在代码前全部自动化，但至少要在实现前明确三类测试：

- 正常流程：用户希望完成什么。
- 异常流程：用户无权限、输入错误、越界、跨租户时如何失败。
- 依赖故障：Keycloak、OPA、DB、Gateway、外部服务异常时如何处理。

## 3. 新增需求流程

### 3.1 输入

新增需求通常是自然语言，例如：

> 支持外部应用通过 API Key 调用业务接口，并沿用现有鉴权体系。

### 3.2 AI 先追问

AI 不直接写代码，而是追问：

1. API Key 属于租户还是系统级？
2. 是否有过期时间、禁用、轮换能力？
3. 是否限制可访问路径？
4. 是否需要资源级 ACL？
5. 明文是否可以落库？
6. 认证失败和鉴权失败分别返回什么？

### 3.3 生成 Spec

Spec 包括：

- 数据结构：`api_keys` 字段、hash、prefix、subject_id、expires_at、allowed_paths。
- 接口契约：创建、查询、更新、轮换、删除。
- 热路径：pep-proxy 识别 `X-API-Key`，认证后合成服务主体身份。
- 安全规则：明文只返回一次，数据库不保存明文。

### 3.4 测试前置

实现前先定义测试：

| 测试 | 预期 |
| --- | --- |
| enabled API Key 访问 allowed path | 允许进入后续 OPA / ACL |
| disabled API Key | 401 |
| expired API Key | 401 |
| API Key 访问非 allowed path | 403 |
| API Key 命中路径但无资源 ACL | 403 |
| 轮换后旧 key | 401 |

### 3.5 实现与验证

AI 读取 Spec 和测试规约后修改：

- IAM API 管理接口。
- pep-proxy 热路径。
- DB schema / migration。
- 自动化测试。
- API 文档和交互记录。

## 4. Bug 修复流程

Bug 修复不是“把报错发给 AI 让它改”，而是按照根因分析协议处理。

### 4.1 标准输入

```markdown
问题：普通用户 A 可以访问普通用户 B 的详情
环境：本地 Kind，AIDP IAM 当前版本
请求路径：/AccessManager/Tenants/{tid}/Users/{uid}/Details
实际结果：200
预期结果：403
复现率：必现
相关日志：OPA input / path_rules / pep-proxy debug
```

### 4.2 失败测试先行

先补充测试：

```text
用用户 A 登录
访问用户 B 的 Details
期望系统拒绝访问
```

### 4.3 根因分析

AI 必须沿链路追溯：

```text
HTTP 结果
  -> Gateway 是否调用 ext_authz
  -> pep-proxy 是否识别身份
  -> OPA input 是否正确
  -> path_rules 数据是否正确
  -> resource_patterns / resource_acl 是否匹配
  -> 初始化数据或历史数据是否漂移
```

### 4.4 最小修复

修复原则：

- 不顺带重构。
- 不改接口签名。
- 不引入新功能。
- 只修复失败测试暴露的问题和同根因问题。

### 4.5 回归沉淀

修复完成后：

- 失败测试转为回归测试。
- issue 状态更新为已修复 / 待确认。
- 如果是通用坑，写入长期记忆或文档。

## 5. 自动运维流程

自动运维用于项目后期稳定化和持续交付，不直接替代生产审批。

### 5.1 触发方式

| 触发 | 动作 |
| --- | --- |
| 每日夜间 | 读取白天 issue，执行自动诊断和可控修复 |
| 每次提交后 | 执行 build、deploy、test、cleanup |
| 发布前 | clean install、uninstall、reinstall、完整测试 |
| 运行异常时 | 汇总日志、定位组件、输出建议 |

### 5.2 自动运维闭环

```text
部署 / 重建
  -> 健康检查
  -> 测试执行
  -> 失败日志收集
  -> AI 归因
  -> 生成修复建议或低风险修复
  -> 回归测试
  -> 报告输出
```

### 5.3 安全边界

AI 自动运维必须遵守：

1. 不直接操作生产环境。
2. 不执行破坏性数据库变更。
3. 不绕过安全扫描和人工审批。
4. 不把敏感日志、密码、token 写入提交材料。
5. 高风险修复只生成建议，由人工确认。

## 6. 上下文工程与长短期记忆

### 6.1 短期记忆

短期记忆记录当前迭代的事实：

- 当天 issue。
- 测试失败日志。
- 本轮修改范围。
- 用户刚做出的设计决策。
- 临时环境状态。

短期记忆的特点是时效性强，适合夜间修复和次日交接。

### 6.2 长期记忆

长期记忆记录跨迭代仍有价值的信息：

- 架构决策和原因。
- 被否定方案。
- 调试陷阱。
- 领域知识。
- Prompt 和 Skills。
- 测试规范。

长期记忆的特点是可继承，适合解决“AI 下次又忘了”的问题。

### 6.3 短期转长期的规则

| 短期信息 | 何时转长期 | 转到哪里 |
| --- | --- | --- |
| 一个偶发 issue | 不转 | issue 日志 |
| 重复出现的坑 | 第二次出现后 | memory / `引用材料/SKILL.md` |
| 架构决策 | 决策当日 | `引用材料/` |
| 测试约束 | 影响后续开发时 | tests / case-test 规范 |
| 黄区可复用流程 | 验证有效后 | 助手 Skill / Prompt |

## 7. 蓝区流程如何迁移到黄区

### 7.1 迁移原则

迁移的是：

- 方法论。
- Prompt 模板。
- Skills。
- 测试规约。
- issue 模板。
- 上下文组织方式。
- 自动化工作流。

### 7.2 黄区流程总览

```text
蓝区：
  在 AIDP IAM / Gateway 中验证流程
  -> 抽象 Prompt / Skills / 测试模板 / issue 模板
  -> 脱敏和安全审查

黄区：
  使用黄区 Agent 和黄区数据
  -> IT 助手补 UT
  -> 产研助手做 Spec / 测试 / DTS / 记忆
  -> 运维助手做采集 / 诊断 / 报告
  -> 结果沉淀回黄区知识库
```

### 7.3 三个助手在黄区流程中的位置

| 阶段 | 黄区助手 | 作用 |
| --- | --- | --- |
| 需求 / Spec | 产研助手 | 结构化需求、文档一致性、DTS 草稿、知识溯源 |
| 测试前置 / UT | IT 助手 | 环境感知、CodeAgent 内嵌、覆盖率提升、Skills 迭代 |
| 部署 / 运维 | 运维助手 | 多主机采集、AI 推理、异常诊断、运行报告 |
| 记忆沉淀 | 产研助手 + IT 助手 | 短期问题日记转长期知识卡片或 UT Skill |
| 白+黑 | 三者协同 | 白天收集问题，夜间自动分析、修复或生成建议 |

## 8. 可直接复用的 Prompt

### 新需求

```text
读取项目约束、架构文档和相关 Story。
我有一个新增需求：[需求描述]。
请先追问隐含约束，不要直接写代码。
澄清后输出：结构化功能点、接口契约、测试规约、依赖故障场景。
```

### TDD 实现

```text
基于以下 Spec 和测试规约实现功能。
要求先补充失败测试或验收用例，再修改代码。
实现后运行相关测试，并说明每个测试覆盖的业务行为。
```

### Bug 修复

```text
以下是完整问题记录和日志：[问题记录]。
请先生成复现用例，再沿调用链追溯根因。
修复前先说明影响范围。
修复时不引入新功能、不改接口签名、不顺带重构。
```

### 白+黑夜间修复

```text
读取今天的 issue 日志。
按 P0 -> P1 -> P2 分类处理。
逐条根因分析，合并同根因问题。
修复完成后更新 issue 状态，补充回归测试，输出次日交接摘要。
```

### 短期转长期记忆

```text
请复盘本轮 issue 和修复记录。
判断哪些内容应该沉淀为长期记忆：
1. 被否定方案
2. 调试陷阱
3. 新增测试规则
4. 可复用 Prompt / Skill
输出建议写入位置和内容摘要。
```
