# 创新点：测试即规约与 AI-TDD

> 一句话定位：把测试从“实现后的检查”前移为“实现前的规约”，让 AI 先理解什么行为必须成立，再生成代码。

本文采用 `引用材料/ai-dev-workflow.md` 的结构组织，用于详细说明本项目如何实践“测试即规约”和测试驱动开发。

## TRIGGER：什么时候启用

满足以下任一条件时，必须启用测试即规约：

| 场景 | 说明 |
| --- | --- |
| 新增需求 | 需求尚未实现，需要先定义验收行为 |
| 鉴权逻辑变更 | 涉及 JWT、API Key、OPA、ACL、角色矩阵等安全边界 |
| Bug 修复 | 先把 Bug 固化成失败用例，再修复 |
| 业务接入 | 新应用接入 Gateway，需要校验路由、鉴权和 ACL 同步 |
| 发布前回归 | 需要确认核心路径、异常路径和依赖故障路径 |

不适用场景：

- 纯文字修订。
- 明确不影响行为的样式调整。
- 单个注释或无逻辑变更的格式化。

## WORKFLOW：AI-TDD 标准流程

### Phase 1：把需求转为行为

用户给出自然语言需求后，AI 先输出行为清单：

```text
谁在什么前置条件下
执行什么操作
系统应该返回什么结果
哪些情况必须拒绝
依赖服务失败时应该怎么处理
```

示例：

```text
需求：支持 API Key 调用业务接口。

行为：
1. enabled 且未过期的 API Key 可进入 OPA 和 ACL 鉴权。
2. disabled API Key 被认证层拒绝。
3. expired API Key 被认证层拒绝。
4. API Key 访问非 allowed_paths 被路径约束拒绝。
5. API Key 通过路径约束后仍必须通过 resource_acl。
```

### Phase 2：生成测试矩阵

测试矩阵必须覆盖三类场景：

| 类别 | 目标 | 示例 |
| --- | --- | --- |
| 正常流程 | 功能应该成功 | API Key 访问允许路径 |
| 异常操作 | 用户操作不合规时应拒绝 | API Key 过期、跨租户、无 ACL |
| 依赖故障 | 外部组件异常时应安全失败 | OPA 不可用、DB 超时、Keycloak 故障 |

### Phase 3：先写失败用例或验收用例

根据任务风险选择测试形态：

| 风险 | 测试形态 |
| --- | --- |
| 高风险鉴权热路径 | 自动化集成测试 |
| 中风险业务流程 | 黑盒测试用例 + 部分自动化 |
| 低风险 UI 或文档 | 人工验收清单 |

Bug 修复必须先有失败用例。没有失败用例时，AI 容易只修现象。

### Phase 4：AI 实现代码

AI 实现时必须遵守：

1. 只实现测试矩阵覆盖的行为。
2. 不自行扩展未确认功能。
3. 不改变已锁定接口签名。
4. 对每个失败路径给出明确错误语义。
5. 实现完成后说明每个测试对应哪段业务行为。

### Phase 5：运行验证

验证顺序：

```text
局部测试
  -> 相关模块集成测试
  -> Gateway 黑盒测试
  -> clean install / reinstall 验证
```

### Phase 6：测试沉淀

完成后沉淀：

- 新增测试文件。
- 更新 DT 用例说明。
- 将 Bug 转成回归用例。
- 把新发现的测试盲区写入 `引用材料/ai-dev-workflow.md` 或主说明书。

## PROMPT TEMPLATES：可复用提示词

### 新需求测试规约

```text
读取 引用材料/ai-dev-workflow.md 和相关 Story。
针对以下需求生成测试规约，不要先写代码：
[需求描述]

输出：
1. 行为清单
2. 正常流程测试
3. 异常操作测试
4. 依赖服务故障测试
5. 推荐自动化范围
```

### Bug 复现测试

```text
以下是 Bug 记录：
[问题现象、环境、复现步骤、预期结果]

请先生成失败测试或回归用例，再分析可能根因。
不要直接修改代码。
```

### 实现前检查

```text
请检查当前测试矩阵是否足够约束实现。
重点检查：
1. 是否覆盖无权限和跨租户
2. 是否覆盖依赖服务不可用
3. 是否明确错误语义
4. 是否有可执行验证命令
```

## METRICS：效果指标

| 指标 | 含义 | 目标 |
| --- | --- | --- |
| 测试前置率 | 新需求实现前已有测试规约的比例 | > 80% |
| 负向用例覆盖率 | 权限、异常、依赖故障用例占比 | > 40% |
| Bug 回归沉淀率 | 修复后补充回归用例的比例 | > 90% |
| 首次实现通过率 | AI 实现后首次测试通过比例 | 持续提升 |
| 重复 Bug 率 | 同类问题二次出现比例 | 持续下降 |

## AIDP IAM 示例

### 示例一：普通用户访问他人详情

测试规约：

```text
前置：存在普通用户 A 和普通用户 B。
步骤：A 登录后访问 B 的 Details 页面。
预期：系统拒绝访问。
```

价值：

- 这个测试先定义了“普通用户只能看自己”的行为。
- 修复时 AI 沿 OPA、path_rules、DB 初始化、self-only 检查追根因。
- 修复后该用例成为权限回归测试。

### 示例二：API Key 统一鉴权

测试规约：

```text
API Key 认证成功后不能直接放行业务请求，必须继续走 OPA 和 resource_acl。
```

价值：

- 避免实现成第二套旁路权限系统。
- 让机器访问和用户访问复用同一套安全模型。

## ANTI-PATTERNS：反模式

| 反模式 | 后果 | 正确做法 |
| --- | --- | --- |
| 先让 AI 写代码，再补测试 | 容易按 AI 的实现反推测试 | 先写行为和失败路径 |
| 只测成功路径 | 权限系统容易漏绕权 | 正常、异常、故障三类必测 |
| Bug 没复现就修 | AI 可能修错目标 | 先生成失败用例 |
| 用代码细节写测试 | 测试脆弱，重构即失效 | 从业务行为写测试 |
