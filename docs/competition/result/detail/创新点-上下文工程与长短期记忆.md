# 创新点：上下文工程与长短期记忆

> 一句话定位：把“让 AI 理解项目”从每次对话里的口头解释，升级为可版本化、可检查、可复用的工程资产。

## TRIGGER：什么时候启用

只要任务不属于单文件小改，都应启用上下文工程。尤其是：

| 场景 | 为什么需要上下文 |
| --- | --- |
| 新需求设计 | AI 必须知道已有架构和被否定方案 |
| 鉴权逻辑修改 | AI 必须理解 JWT、OPA、ACL、Gateway 的边界 |
| Bug 修复 | AI 必须知道调用链、测试命令和历史坑 |
| 跨会话继续开发 | AI 必须恢复上次决策和当前状态 |
| 黄区迁移 | AI 必须只迁移流程，不迁移敏感数据 |

## PROBLEM：没有上下文工程会发生什么

AI 改代码理解不准确，通常不是模型能力问题，而是上下文资产缺失：

1. **完整性不足**：AI 不知道某个接口已有约束，生成了冲突逻辑。
2. **时效性不足**：AI 依据过时文档修改代码。
3. **密度不足**：关键信息混在大量聊天记录里，AI 抓不住重点。
4. **记忆缺失**：AI 重复提出已经被否定的方案。
5. **边界不清**：AI 在修 Bug 时顺带重构或改接口。

## MEMORY MODEL：长短期记忆模型

### 短期记忆

短期记忆服务当前任务，生命周期通常是一天到一个迭代。

| 内容 | 示例 |
| --- | --- |
| 当日 issue | 白天测试发现的 P0/P1/P2 问题 |
| 当前环境 | 当前分支、部署状态、测试失败输出 |
| 本轮决策 | 今天确认“不改接口签名” |
| 临时结论 | 某个错误暂判为环境问题 |

### 长期记忆

长期记忆服务后续任务，生命周期随项目存在。

| 内容 | 示例 |
| --- | --- |
| 架构决策 | OPA 只做路径级鉴权，resource_acl 做实例级鉴权 |
| 被否定方案 | 不把 resource_acl 全量推入 OPA |
| 调试陷阱 | `WHERE NOT EXISTS` 不能覆盖存量初始化数据 |
| 领域规范 | 统一 URL、角色矩阵、API Key 明文不落库 |
| 可复用工具 | Prompt、Skills、测试模板、issue 模板 |

## CONTEXT LOADING：上下文加载顺序

AI 不应一次性读取全部文档，而应按任务加载最小闭包。

### 新需求

```text
引用材料/ai-dev-workflow.md
  -> 引用材料/AI-programm-practice.md
  -> 引用材料/practice-process.md
  -> 相关代码或测试
```

### Bug 修复

```text
issue 记录
  -> 错误日志
  -> 引用材料/practice-process.md
  -> 相关代码或测试
  -> 历史 error / todo
```

### 夜间白+黑

```text
当天 issue 列表
  -> 测试命令
  -> 修改边界
  -> 历史调试陷阱
  -> 输出次日摘要
```

## WORKFLOW：上下文工程工作流

### Phase 1：建立上下文入口

固定入口包括：

- `引用材料/ai-dev-workflow.md`
- `引用材料/AI-programm-practice.md`
- `AI友好型软件工程固化流程.md`

它们告诉 AI：

1. 项目是什么。
2. 当前流程怎么跑。
3. 哪些目录是关键资产。
4. 哪些事情不能做。

### Phase 2：任务前上下文选择

AI 开始任务前先回答：

```text
当前任务需要哪些上下文？
哪些文档必须读？
哪些文档不需要读？
哪些信息可能过时，需要以代码或测试为准？
```

### Phase 3：执行中维护短期状态

执行过程中维护：

- 已完成步骤。
- 当前失败点。
- 已排除原因。
- 下一步验证命令。

这能支持夜间长任务不中断。

### Phase 4：结束时沉淀长期记忆

每个任务结束时复盘：

| 问题 | 判断 |
| --- | --- |
| 是否出现新架构决策 | 写入架构文档 |
| 是否否定了某方案 | 写入 Q&A 或记忆 |
| 是否出现可复用 Prompt | 写入创新点文档或 Skills |
| 是否出现新测试盲区 | 写入测试规约 |
| 是否只是一时环境问题 | 留在短期 issue，不进入长期 |

| 产物 | 作用 |
| --- | --- |
| 上下文加载清单 | 说明 AI 本轮依据哪些材料工作 |


## METRICS：衡量指标

| 指标 | 说明 |
| --- | --- |
| 首次生成合格率 | AI 生成代码无需大改即可通过测试和 review 的比例 |
| 重复踩坑次数 | 同类 Bug 或同类错误建议重复出现次数 |
| 上下文恢复时间 | 新会话恢复项目状态所需时间 |
| 记忆命中率 | AI 是否主动应用了已有决策和陷阱记录 |
| 文档漂移率 | 文档与代码或测试不一致的比例 |

## AIDP IAM 示例

### 记忆一：resource_acl 不推入 OPA

结论：

> OPA 只做路径级鉴权，resource_acl 直接查 PostgreSQL。

原因：

- path_rules 数据量小，适合 OPA 内存策略。
- resource_acl 数据量大，推入 OPA 会造成内存和更新压力。
- 实例权限需要实时变更，数据库查询更直接。

### 记忆二：API Key 不做旁路授权

结论：

> API Key 认证成功后合成服务主体，继续走 OPA 和 ACL。

原因：

- 避免机器访问绕过用户访问的安全模型。
- 减少第二套权限体系的设计和测试成本。

### 记忆三：初始化数据不能只用 WHERE NOT EXISTS

结论：

> 初始化规则变更时必须考虑存量数据更新。

原因：

- `WHERE NOT EXISTS` 只保证新环境插入。
- 已有环境可能保留旧规则，导致 OPA 数据不符合最新预期。
