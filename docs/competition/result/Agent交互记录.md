# Agent 交互记录整理版

本文用于作为提交材料中的 `agent交互记录.md` 基础稿。内容按代表性场景整理，不逐字复制全部对话，重点呈现 AI 在需求澄清、测试前置、代码实现、Bug 修复、自动运维和记忆沉淀中的作用。

## 1. 需求澄清：统一鉴权系统初始设计

### 用户输入

> 我们需要为多个业务应用设计统一鉴权方案，支持用户登录、API 鉴权、资源级权限控制、多租户隔离。

### Agent 追问

1. 租户隔离粒度是什么，是 realm、schema、行级还是仅路径隔离？
2. 鉴权发生在网关层、应用层，还是两者都有？
3. 路径权限是静态配置，还是应用注册后动态生成？
4. 资源 ACL 是创建时自动生成，还是业务主动调用 IAM 写入？
5. 外部应用通过 API Key 访问时，是否复用同一套 OPA 和 ACL？
6. 依赖服务不可用时是 fail-open 还是 fail-close？

### 形成的关键决策

| 决策 | 结果 |
| --- | --- |
| 认证入口 | JWT 和 API Key 都由 pep-proxy 统一处理 |
| 路径级鉴权 | OPA 负责路径和方法级 allow / deny |
| 资源级鉴权 | PostgreSQL `resource_acl` 负责具体资源实例权限 |
| ACL 同步 | resource-sync 通过 Envoy ext_proc 在响应阶段自动写入或清理 |
| 默认行为 | 鉴权失败默认拒绝 |

### 价值

AI 没有直接给代码，而是先把隐含约束挖出来，避免后续实现阶段出现权限语义返工。

## 2. 测试前置：把需求变成测试规约

### 用户输入

> 基于用户管理、API Key、ACL、Gateway 路由，生成测试用例。

### Agent 输出约束

1. 必须覆盖正常流程、异常操作、依赖服务故障。
2. 每个功能点至少一条正向用例和一条异常或故障用例。
3. 从黑盒视角描述，不暴露内部 API 参数。
4. 测试步骤和预期结果数量一致。
5. 依赖服务故障必须覆盖 Keycloak、OPA、PostgreSQL 等。

### 示例测试规约

| 用例名称 | 场景 | 预期 |
| --- | --- | --- |
| 普通用户查看自己详情成功 | 正常流程 | 登录后能看到自己的用户详情 |
| 普通用户查看他人详情失败 | 权限异常 | 系统拒绝访问他人详情 |

| OPA 不可用导致业务访问失败 | 依赖故障 | 系统 fail-close，不放行请求 |

### 价值

测试从实现后检查前移到实现前规约，AI 编码时目标更明确，人工评审也有客观依据。

## 3. 代码生成：API Key 统一身份模型

### 用户输入

> 实现 API Key 管理和热路径认证，但不要做第二套授权系统，必须复用 OPA 和 resource_acl。

### Agent 理解

API Key 不应只做密钥校验后直接放行，否则会绕过统一鉴权。正确做法是：

1. IAM API 负责创建、查询、更新、轮换、禁用、删除 API Key。
2. 明文 Key 只在创建和轮换时返回一次。
3. 数据库只保存 hash、key prefix、subject_id、allowed_paths、expires_at。
4. pep-proxy 识别 `X-API-Key` 后校验状态和路径。
5. 校验通过后合成服务主体身份，继续进入 OPA 和 resource_acl。

### 生成/修改范围

- `apps/iam-api/`
- `apps/pep-proxy/`
- DB schema / 初始化数据
- API Key 相关自动化测试
- API 文档

### 价值

AI 生成的不只是 CRUD，而是符合架构约束的统一身份模型，避免了机器访问绕过权限系统的安全风险。

## 4. Bug 修复：普通用户访问他人详情权限放大

### 用户输入

> 普通用户 A 访问用户 B 的 Details 接口返回 200，预期应该拒绝。

### Agent 排查链路

```text
现象：普通用户 A 可以访问用户 B 的详情
  -> 检查 Gateway 是否触发 ext_authz
  -> 检查 pep-proxy 身份解析
  -> 检查 OPA 输入和 path_rules
  -> 检查 DB init SQL 是否覆盖存量数据
  -> 检查 self-only 逻辑是否在 AccessManager bypass 之前执行
```

### 根因

初始化 SQL 使用 `WHERE NOT EXISTS`，导致已有 `path_rules` 没有被新规则覆盖；同时 self-only 检查位置靠后，存在绕过路径。

### 修复策略

1. 补充处理存量数据的更新逻辑。
2. 将 self-only 检查前移到更早的位置。
3. 增加普通用户访问他人详情失败的回归测试。

### 价值

这是“根因分析而非症状修复”的典型案例。AI 没有停留在表面 200/403，而是追到数据初始化语义和调用链位置。

## 5. 白+黑协作：夜间 issue 消化

### 白天输入

人工测试记录：

```markdown
### P1 影响体验
- [ ] 现象：创建资源后立即访问详情失败
  环境：Kind 本地集群，普通用户
  实际结果：403
  预期结果：创建者应拥有 Owner 权限
  复现率：必现
```

### 夜间 Agent 处理

1. 判断问题类型：ACL 自动同步失败。
2. 检查 resource-sync 是否收到响应。
3. 检查响应体是否能提取资源 ID。
4. 检查 `resource_patterns` 中 `response_id_field`。
5. 检查 pending retry 是否写入。
6. 修复提取逻辑或配置。
7. 补充“创建资源后创建者拥有 Owner 权限”的回归测试。

### 次日摘要

```text
昨日修复：1 个 P1
待人工确认：创建资源后详情访问
设计问题待决策：无
新增回归用例：1 条
```

### 价值

白天人工专注真实使用体验，夜间 AI 做批量根因分析和一致性修复，降低上下文切换成本。

## 6. 上下文工程：长期记忆与短期记忆

### 用户输入

### Agent 方案

建立三层上下文和长短期记忆：

| 层级 | 内容 | 示例 |
| --- | --- | --- |
| 项目约束 | 每次会话必须遵守 | `detail/引用材料/ai-dev-workflow.md`、部署命令、路径规范 |

| 记忆资产 | 被否定方案、调试陷阱、用户偏好 | memory、知识卡片、Skills |

短期记忆：

- 当日 issue。
- 当前测试失败。
- 本轮修改范围。

长期记忆：

- 架构决策。
- 被否定方案。
- 调试陷阱。
- 可复用 Prompt / Skills。

### 价值

上下文工程把“让 AI 理解项目”从每次口头解释，变成可版本化、可复用、可检查的工程资产。

## 7. 黄区助手迁移：IT / 产研 / 运维

### 用户输入

> 蓝区流程怎么迁移到黄区？IT 助手、产研助手、运维助手怎么放进去？

### Agent 整理

蓝区迁移到黄区时，迁移的是流程和资产模板，不迁移敏感数据。

| 蓝区能力 | 黄区承接助手 | 迁移动作 |
| --- | --- | --- |
| 测试即规约 / UT 生成 | IT 助手 | 环境感知、覆盖率分析、UT Skills、自动迭代 |
| 上下文工程 / 记忆 | 产研助手 | 双轨记忆、知识溯源、DTS 草稿、测试生成 |
| 自动运维 / 日志归因 | 运维助手 | SSH 采集、LLM 推理、诊断报告、健康检查 |

### 价值

提交材料体现的不只是一个蓝区工程，而是一套能在黄区真实研发、测试、运维场景落地的组织级方法。
