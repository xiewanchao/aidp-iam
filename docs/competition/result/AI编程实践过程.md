### 1.1 背景

AIDP IAM / Gateway 项目需要为多个业务应用提供统一认证、统一鉴权和统一入口治理能力。请求从 Envoy Gateway 进入后，需要经过身份认证、路径级鉴权、资源实例级鉴权，并在资源创建、删除、列表查询过程中自动维护和注入权限信息。

该项目不是单文件、单服务的小工具，而是一个多组件、多协议、多运行态的复杂工程，涉及：

- Keycloak：统一身份、登录流、用户组、外部 IdP。
- Envoy Gateway：统一入口、HTTPRoute、SecurityPolicy、ext_authz、ext_proc。
- OPA：路径级策略鉴权。
- PostgreSQL：API Key、path rules、resource ACL、pending ACL。
- pep-proxy：JWT / API Key 认证、OPA 调用、resource_acl 查询。
- bundle-server：OPA policy/data 生成。
- resource-sync：资源生命周期中的 ACL 自动同步和列表过滤 header 注入。
- gateway-manager：证书管理与 OMS 日志回调支撑能力。

传统开发这类项目的主要损耗不在写代码，而在：

1. 需求隐含约束多，容易在实现后才发现权限语义不一致。
2. 跨组件契约多，OPA、DB、Gateway、Keycloak、业务后端任一处变更都可能引入不一致。
3. 测试组合复杂，多租户、多角色、多资源、依赖服务故障场景人工很容易遗漏。
4. AI 跨会话容易遗忘上下文，重复提出已被否定的方案，或者基于过时理解改代码。

本项目的核心实践是将 AI 放入软件工程全流程，而不是只让 AI 参与代码生成。我们把项目约束、架构文档、测试用例、部署脚本、问题日志和经验记忆建设为 AI 可消费的工程资产，让 AI 在正确上下文中进行需求澄清、规约生成、代码实现、测试补充、部署验证、Bug 修复和运维闭环。

### 1.2 业务背景

IAM 作为基础身份与权限组件，为业务提供用户登录、组管理、应用注册、路径授权、API Key 认证、资源 ACL 授权和 Manifest 注册能力。Gateway 作为统一入口，负责业务路由、证书入口、流量治理和鉴权策略挂载。

当前统一鉴权体系按三层展开：

1. **身份认证层**：用户侧使用 Keycloak JWT，外部系统侧使用 API Key。pep-proxy 统一识别 `Authorization` 或 `X-API-Key`，认证成功后形成统一调用方身份。
2. **路径级鉴权层**：bundle-server 将 `apps`、`path_rules`、`permission_groups` 等数据生成 OPA policy/data，pep-proxy 调用 OPA 判断请求路径和方法是否允许访问。
3. **资源级鉴权层**：pep-proxy 解析统一 URL 中的 tenant、namespace、resource id，查询 `resource_acl`，按 Owner、Contributor、Viewer 等角色矩阵判断资源实例是否可访问。

本次比赛材料的主张是：AIDP IAM / Gateway 是蓝区复杂工程样板，IT 助手、产研助手、运维助手是这套 AI 友好型软件工程在黄区的迁移落点。

### 2.1 总体流程：从“代码生成”升级为“工程闭环”

实践流程从原来的“需求 -> 实现 -> 测试”调整为：

```text
需求输入
  -> 上下文加载
  -> 结构化 Spec
  -> 测试即规约 / TDD 用例先行
  -> AI 生成或修改代码
  -> 自动化验证
  -> 白+黑验收
  -> 文档与记忆沉淀
```

关键变化是测试前置。AI 不先写代码，而是先帮助把验收标准、失败路径、依赖故障场景转为可执行或可人工执行的测试规约。代码实现以这些测试为目标，避免“代码写完才讨论需求理解是否正确”。

### 2.3 测试即规约 + TDD：测试前置到实现之前

在新增需求中，流程调整为：

```text
业务需求
  -> 结构化功能点
  -> 验收标准
  -> DT / 集成 / 黑盒 / 依赖故障测试设计
  -> 失败测试或待验收用例
  -> AI 实现代码
  -> 自动化测试通过
```

本项目测试即规约包含四类：

1. **业务验收测试**：从用户视角描述功能是否符合预期，不暴露内部 API 参数。
2. **接口契约测试**：验证统一 URL、HTTP Method、返回结构、分页字段、错误体。
3. **安全负向测试**：无 token、错误 token、跨租户、无 ACL、API Key 过期、allowed_paths 不匹配。
4. **依赖故障测试**：Keycloak、OPA、PostgreSQL、resource-sync、Gateway 策略不可用时的行为。

典型例子：

| 功能点 | 测试规约先行 |
| --- | --- |
| 普通用户查看个人详情 | 普通用户只能查看自己，不能访问他人详情 |
| API Key 访问业务路径 | enabled、expires_at、allowed_paths 同时满足才允许 |
| resource-sync 创建资源 | 创建成功后自动写入 Owner ACL，失败进入 pending retry |
| 列表查询过滤 | 后端只能看到 `X-Allowed-Ids` 限定的资源集合 |

Bug 修复也使用测试驱动：先把 Bug 固化为复现用例或回归测试，再修代码。这样可避免 AI 只修现象、不修根因。

### 2.4 规约驱动开发：先锁定身份、路径、资源和异常行为

在 IAM / Gateway 项目中，规约不是只写接口字段，而是覆盖权限语义：

1. 身份来源：JWT 和 API Key 统一进入 pep-proxy，不形成两套授权体系。
2. 路径级鉴权：OPA 只判断某类路径和方法能否访问。
3. 资源级鉴权：`resource_acl` 判断具体资源实例能否访问。
4. ACL 同步：创建资源写 Owner ACL，删除资源清理 ACL，列表查询注入可见资源。
5. 默认行为：鉴权失败默认拒绝，跨租户默认拒绝，依赖异常按 fail-close 处理。

AI 在编码时必须围绕这些规约生成实现，而不是自行发明新的鉴权语义。

### 2.5 新增需求实践流程

新增需求不直接进入代码实现，而是按以下步骤：

| 阶段 | 人工职责 | AI 职责 | 产物 |
| --- | --- | --- | --- |
| 需求输入 | 给出业务目标和边界 | 追问隔离粒度、鉴权位置、数据性质、依赖服务、性能基线 | 结构化功能点 |
| Spec 定义 | 决策接口和权限语义 | 生成接口契约、数据模型、异常路径 | Story / 设计文档 |
| 测试前置 | 确认验收口径 | 生成 DT、黑盒、依赖故障测试 | 测试用例 / test.py |
| 代码实现 | 审核关键设计 | 按 Spec 和测试实现代码 | 服务代码、配置、Helm |
| 验证闭环 | 判断业务价值 | 运行测试、定位失败、修复问题 | 测试报告 |
| 记忆沉淀 | 选择高价值经验 | 将坑点整理为文档或记忆卡片 | result 文档 / memory 模板 |

### 2.6 Bug 修复实践流程

Bug 修复以完整错误上下文和根因分析为核心：

```text
完整现象
  -> 复现步骤
  -> 失败测试或回归用例
  -> 调用链追踪
  -> 根因定位
  -> 最小修改
  -> 回归测试
  -> 文档/记忆更新
```

典型案例：普通用户访问他人详情的权限放大问题。

表面现象是用户 A 能访问用户 B 的详情。AI 没有停留在“加一个判断”层面，而是沿链路追溯：

```text
HTTP 200 异常放行
  -> OPA 未拒绝
  -> path_rules 数据不匹配
  -> DB init SQL 使用 WHERE NOT EXISTS
  -> 存量规则未被新规则覆盖
  -> pep-proxy self-only 检查位置不正确
```

最终修复不是只改 OPA，而是同时处理初始化数据和 self-only 检查位置，并补充回归测试。

### 2.7 白+黑协作验收

白+黑是本项目的核心流程创新之一。它不是“晚上让 AI 加班”，而是把人和 AI 分配到各自最适合的任务。

白+黑为什么能跑一晚上、Todo list 应该细到什么程度、AI 何时停止，详见 [`detail/创新点-白加黑协作模式.md`](detail/创新点-白加黑协作模式.md)。

| 时间 | 主体 | 任务 | 纪律 |
| --- | --- | --- | --- |
| 白天 | 人工 | 使用真实业务场景探索问题，记录 issue、环境、预期、复现率 | 不临时补丁，不打乱现场 |
| 夜间 | AI | 读取 issue，分类、根因分析、批量修复、补回归测试 | 不引入新功能，不改接口签名 |
| 次日 | 人工 | 验证修复，确认设计问题，继续探索 | 先验收昨日修复再进入新一轮 |

问题日志格式：

```markdown
## YYYY-MM-DD 测试问题记录

### P0 阻断
- [ ] 现象：[操作步骤] -> [实际结果] vs [预期结果]
  环境：[版本 / 账号 / 数据状态]
  复现率：必现 / 偶现

### P1 影响体验
- [ ] 现象：...

### P2 细节
- [ ] 现象：...
```

次日交接摘要：

```text
昨日修复：X 个（P0: N，P1: N，P2: N）
待人工确认：X 个
设计问题待决策：X 个
新增回归用例：X 条
```

### 2.8 自动运维与持续验证

最后阶段引入自动运维，把 AI 协作从开发延伸到部署、验证和运行态反馈：

1. **自动部署验证**：通过 `代码/deploy/scripts/setup.sh`、`代码/deploy/scripts/test.sh`、`代码/deploy/scripts/cleanup.sh` 形成 clean install、uninstall、reinstall 闭环。
2. **自动健康检查**：检查 Gateway、IAM、OPA、Keycloak、PostgreSQL、业务 mock 是否正常。
3. **自动日志归因**：测试失败时，AI 根据日志定位是配置、数据、代码还是环境问题。
4. **自动回归报告**：输出失败用例、影响范围、修复建议和下一步人工确认点。
5. **安全边界**：生产部署、数据库变更、安全策略修改必须人工审批；AI 不直接执行破坏性操作。

自动运维不是替代运维人员，而是把重复诊断、日志汇总、测试验证和报告生成自动化，让人工保留最终决策权。

自动运维和根因分析闭环详见 [`detail/自动运维与根因分析闭环.md`](detail/自动运维与根因分析闭环.md)。

1. Gateway 接入从手写多份 YAML，收敛为通过生成器生成 HTTPRoute、ReferenceGrant、SecurityPolicy、EnvoyExtensionPolicy 和 ACL 同步配置。
2. API Key 不再旁路实现权限，直接复用 OPA 和 ACL，减少设计、测试和安全审查成本。
3. resource-sync 自动处理资源创建、删除、列表过滤，业务后端无需自建权限中心。
4. DT 测试用例由 AI 从业务行为推导，覆盖正常、异常、依赖故障三类场景。
5. 白+黑模式把人工探索和 AI 批量修复拆开，减少上下文切换和临时补丁带来的返工。

### 3.2 质量提升点

1. 鉴权默认拒绝，无 token、错误 token、路径权限不足、资源 ACL 不足、跨租户访问均不能到达后端。
2. JWT 与 API Key 统一进入 pep-proxy，不存在双链路语义不一致。
3. API Key 明文只在创建和轮换时返回一次，数据库只保存 hash 和 key prefix。
4. 资源 ACL 使用最长前缀匹配，子资源继承父资源权限，不需要为每个子路径重复授权。
5. 依赖故障测试前置，Keycloak、OPA、DB、Gateway 策略异常不再依赖生产事故暴露。
6. 代码、文档、测试、记忆同步更新，降低 AI 后续基于过时上下文改代码的风险。

## 6、加分项说明

### 6.1 Spec Driven Development

本项目先形成鉴权 Story、Manifest 规范、资源路径规范、API Key 语义、ACL 同步规则，再由 AI 实现代码。核心价值是把“身份、路径、资源、角色、异常行为”提前锁定，减少实现后返工。

### 6.2 代码质量

1. 鉴权热路径集中在 pep-proxy，管理面集中在 iam-api，策略生成集中在 bundle-server，ACL 同步集中在 resource-sync。
2. 代码修改遵循 clean code 约束：函数职责、复杂度、参数数量、错误处理、命名规范。
3. 安全逻辑有负向测试：跨租户、无权限、API Key 失效、依赖服务故障。
4. 部署配置固定镜像版本、无硬编码密钥、敏感信息不进入提交材料。

### 6.3 可演进性

1. 新业务通过 Manifest、path rules、HTTPRoute、SecurityPolicy 接入，不改鉴权核心。
2. 新角色、新资源、新应用可以通过规约扩展。
3. 新问题进入短期 issue，复盘后沉淀为长期记忆或测试规约。
4. IT、产研、运维三个助手分别承接测试、研发治理、运维诊断，让流程能迁移到不同业务线。

## 7、问题记录

| 问题 | 现象 | 解决思路 | 沉淀 |
| --- | --- | --- | --- |
| AI 容易按表面报错改代码 | 403 / 200 异常时直接改判断 | 要求沿 HTTP -> OPA -> DB -> 初始化数据追根因 | 根因分析 Prompt |
| 测试后置导致返工 | 代码写完才发现权限语义不一致 | 测试即规约，先写验收和失败路径 | TDD 流程 |
| 跨会话遗忘 | AI 重复提出已否定方案 | 建立项目约束、设计文档、长期记忆 | 上下文工程 |
| 白天边测边修干扰大 | 临时补丁掩盖真实问题 | 白天只记录，夜间统一修复 | 白+黑流程 |
| 蓝区方法难直接进黄区 | 数据、工具、环境边界不同 | 迁移流程和模板，不迁移敏感数据 | 三助手黄区落地 |

个人思考：

1. AI 辅助开发的关键不是让 AI 写更多代码，而是让 AI 在正确上下文、正确测试和正确边界里工作。
2. 测试即规约能把需求理解从口头共识变成可验证资产，是降低 AI 偏差的核心手段。
3. 长短期记忆不是“聊天记录归档”，而是把经验分层沉淀为下一轮开发可复用的工程上下文。
4. 黄区推广时要强调迁移的是方法、Prompt、Skills 和流程，所有真实数据和执行动作都在黄区闭环。
