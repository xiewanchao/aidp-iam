# PPT 制作 Prompt 与介绍视频脚本

## 0. 可直接复制给 PPT 生成工具的 Prompt

```text
你是一名企业级 AI 创新赛 PPT 策划与视觉设计专家。请基于以下提交材料，生成一份 14-15 页的中文答辩 PPT 大纲和逐页文案，并为每页补充讲稿备注。

材料范围只使用当前 result 文件夹：
1. AI编程实践过程.md：主说明书和总览。
2. Agent交互记录.md：代表性人机协作场景。
3. detail/AI友好型软件工程固化流程.md：固化流程详细说明。
4. detail/创新点-测试即规约与TDD.md：测试前置和 TDD。
5. detail/创新点-上下文工程与长短期记忆.md：上下文工程与记忆体系。
6. detail/创新点-白加黑协作模式.md：白天人工、夜间 AI 的实现机制。
7. detail/AI编程实践流程-蓝区到黄区.md：黄区迁移和三助手落地。
8. detail/自动运维与根因分析闭环.md：自动运维与根因分析。
9. detail/效率收益与人力节省测算.md：代码规模、人力节省和提效数据。
10. detail/IT助手/、detail/产研助手/、detail/运维助手/：黄区三个助手材料。

核心叙事：
- 不要把作品讲成“用 AI 写了一个 IAM 项目”。
- 要讲成“用 AIDP IAM / Gateway 这个复杂工程验证了一套 AI 友好型软件工程方法”。
- IAM / Gateway 是蓝区复杂工程样板；黄区用 IT 助手、产研助手、运维助手承接研发、测试、运维场景。
- 主创新包括：AI 友好型软件工程、测试即规约与 TDD、上下文工程与长短期记忆、白+黑协作、蓝区到黄区迁移、自动运维与根因分析闭环。

必须呈现的关键数据：
- 核心应用代码约 2.7 万行。
- 活跃工程资产约 7.1 万行。
- 含文档和配置资产约 9.3 万行。
- 传统开发估算 60-95 人日。
- AI 辅助后估算 23-39 人日。
- 人力节省约 37-56 人日，节省比例约 50%-60%。

必须有的图：
1. AI 友好型软件工程流水线图：任务识别 -> 上下文加载 -> Spec -> 测试规约 -> 实现 -> 验证 -> 白+黑 -> 记忆沉淀。
2. 测试即规约流程图：需求 -> Spec -> 测试 -> 实现 -> 验证。
3. 上下文工程图：短期记忆 -> 复盘提炼 -> 长期记忆 -> 下一轮加载。
4. 白+黑闭环图：白天收集 issue -> 夜间 AI 根因分析/修复/回归 -> 次日人工验收。
5. 蓝区到黄区迁移图：蓝区样板 -> 脱敏资产包 -> IT 助手 / 产研助手 / 运维助手。
6. 效率收益表：传统投入、AI 辅助投入、节省人日、单项加速比。

风格要求：
- 企业技术答辩风格，克制、清晰、可信。
- 不要做营销海报式大字空页。
- 每页保留足够证据和数据，不堆砌长段文字。
- 重点页使用流程图、矩阵表、对比表。
- 色彩建议使用深灰、蓝、青、橙少量强调，避免大面积渐变。

请输出：
1. PPT 标题和副标题。
2. 每页标题、页面重点、视觉布局建议、讲稿备注。
3. 3-5 分钟介绍视频脚本。
4. 答辩时可使用的 5 条高密度表达。
```

## 1. PPT 建议结构

建议控制在 12-15 页，主线清晰：一个复杂工程样板，一套方法论，多个创新点详述，三个黄区落点。

### 第 1 页：标题

标题：

> AI 友好型软件工程实践：从蓝区 AIDP IAM 到黄区三助手复制

副标题：

> 上下文工程 + 测试即规约 + 白+黑协作验收

画面建议：

- 左侧：AIDP IAM / Gateway 架构简图。
- 右侧：IT 助手、产研助手、运维助手三个落点。

### 第 2 页：业务痛点

要点：

1. 复杂工程不是“写代码慢”，而是需求理解、跨组件一致性、测试盲区、知识遗忘造成损耗。
2. IAM / Gateway 涉及 Keycloak、OPA、Envoy、PostgreSQL、pep-proxy、resource-sync 多组件。
3. 传统 AI 只会写局部代码，容易理解偏差、重复踩坑。

### 第 3 页：核心方案

标题：

> 让工程对 AI 友好，而不是让 AI 猜工程

图示：

```text
上下文工程
  + 测试即规约
  + Spec Driven
  + 白+黑协作
  + 自动运维
  = AI 友好型软件工程
```

### 第 4 页：AIDP IAM / Gateway 样板

要点：

- JWT / API Key 统一身份。
- OPA 路径级鉴权。
- resource_acl 资源级鉴权。
- resource-sync 自动写 ACL 和列表过滤。
- Gateway 接入生成器降低业务接入成本。

### 第 5 页：测试即规约 + TDD

图示：

```text
需求
  -> Spec
  -> 测试规约
  -> AI 实现
  -> 自动验证
```

讲清楚：

- 测试放到实现前。
- 正常、异常、依赖故障三类用例。
- Bug 先变成失败测试，再修复。

### 第 6 页：上下文工程 + 长短期记忆

图示：

```text
短期记忆：issue / 日志 / 当前决策
        -> 复盘提炼
长期记忆：架构 / 被否定方案 / 调试陷阱 / Skills
```

讲清楚：

- 解决 AI 理解不准确。
- 解决跨会话遗忘。
- 解决同类问题重复踩坑。

### 第 7 页：白+黑协作验收

图示：

```text
白天人工：真实操作 -> 记录问题
夜间 AI：根因分析 -> 修复 -> 回归
次日人工：验证 -> 新一轮探索
```

讲清楚：

- 人负责真实业务判断。
- AI 负责批量系统修复。
- 每个修复都补回归测试。

### 第 8 页：新增需求、Bug 修复、自动运维三条流程

三列展示：

| 新增需求 | Bug 修复 | 自动运维 |
| --- | --- | --- |
| Spec -> 测试 -> 实现 | 复现 -> 根因 -> 回归 | 部署 -> 健康检查 -> 日志归因 |

### 第 9 页：黄区迁移路径

图示：

```text
蓝区 AIDP IAM 样板
  -> 脱敏资产：Prompt / Skills / 测试规约 / issue 模板
  -> 黄区三助手
       IT 助手：UT 和覆盖率
       产研助手：Spec / 测试 / DTS / 记忆
       运维助手：采集 / 诊断 / 报告
```

### 第 10 页：效率与收益

## 2. 答辩表达与评审口径

### 总体定位

不建议说：

> 我们用 AI 写了 IAM 项目。

建议说：

> 我们验证了一套 AI 友好型软件工程方法。IAM / Gateway 是复杂工程样板，测试即规约保证 AI 不写偏，上下文工程和长短期记忆保证 AI 不忘，白+黑保证问题不过夜，三助手保证这套方法能从蓝区迁移到黄区。

### 固化流程

> 我们固化的不是一个提示词，而是一条 AI 可执行的软件工程流水线：需求先结构化，测试先规约，代码按上下文生成，问题按 Todo 夜间消化，经验再沉淀为长期记忆。

### 白+黑模式

> 白+黑不是让 AI 无限制加班，而是把白天人工发现的问题整理成结构化 issue，夜间由 AI 按 Todo、测试命令和安全边界批量做根因分析、低风险修复和回归，次日再由人工验收。

### 蓝区到黄区

> 蓝区不是最终边界，而是方法试验田。我们把在 AIDP IAM 中验证过的 AI 工程流程抽象成 Prompt、Skills、测试规约和 issue 模板，再由黄区 IT 助手、产研助手、运维助手分别承接研发、测试、运维场景。

### 自动运维

> 自动运维不是让 AI 直接操作生产，而是在受控环境中把部署、测试、日志归因和报告生成自动化。AI 负责重复、系统、可回归的诊断工作，人工保留生产审批和高风险决策。

### 效率收益

> 这个项目不是几百行 Demo，而是核心应用约 2.7 万行、活跃工程资产约 7.1 万行的复杂工程。传统开发保守需要 60-95 人日，我们通过上下文工程、测试即规约、AI 代码生成、白+黑修复和自动运维，把投入压缩到约 23-39 人日，节省约 50%-60%。

## 3. 介绍视频脚本

建议 3-5 分钟。

### 0:00-0:30 开场

大家好，我们这次参赛的作品是“AI 友好型软件工程实践”。我们不是单纯展示 AI 写了多少代码，而是展示如何把 AI 放进真实软件工程流程中，让它参与需求、测试、代码、部署、修复和运维。

样板项目是 AIDP IAM / Gateway。它是一个 Kubernetes 上的统一鉴权和网关系统，涉及 Keycloak、Envoy Gateway、OPA、PostgreSQL、pep-proxy、resource-sync 等多个组件，属于典型复杂工程。

### 0:30-1:10 痛点

这类项目最大的成本不是写代码，而是四个问题：

第一，需求隐含约束多，比如 JWT、API Key、路径权限、资源 ACL 的关系必须提前定义清楚。

第二，跨组件一致性难，OPA、数据库、Gateway、Keycloak、业务后端只要一个契约错了，就可能出现绕权。

第三，测试盲区多，多租户、多角色、多资源、依赖故障场景人工容易漏。

第四，AI 跨会话会忘记上下文，容易重复提出已被否定的方案。

### 1:10-2:00 核心方法

我们的核心方法有四个。

第一是上下文工程。我们把项目约束、架构设计、测试脚本、问题日志和经验记忆都变成 AI 可读取的工程资产。AI 每次不是从零开始，而是在正确上下文里工作。

第二是测试即规约。我们把测试放到实现前面，先让 AI 生成正常流程、异常流程、依赖故障的测试规约，再写代码。这样可以减少需求理解偏差。

第三是 Spec Driven。身份、路径、资源、角色、异常行为先形成规约，再生成实现。

第四是白+黑协作。白天人工使用真实业务场景发现问题，只记录不临时补丁；夜间 AI 读取 issue，做根因分析、批量修复和回归测试；第二天人工验收。

### 2:00-2:50 项目落地

在 AIDP IAM / Gateway 中，我们落地了 JWT 和 API Key 统一身份模型、OPA 路径级鉴权、resource_acl 资源级鉴权、resource-sync ACL 自动同步、Gateway 接入生成器。

比如 API Key 没有做成第二套旁路权限系统，而是在认证后转换成服务主体，继续走 OPA 和 resource_acl。

再比如普通用户访问他人详情的问题，AI 没有只改表面判断，而是沿 Gateway、pep-proxy、OPA、DB 初始化数据追到根因，发现是 path_rules 存量数据和 self-only 检查位置问题，并补充了回归测试。

### 2:50-3:40 黄区迁移

这套流程不是只能在蓝区用。我们迁移的不是蓝区数据，而是方法、Prompt、Skills、测试模板和 issue 模板。

在黄区，IT 助手承接 UT 补充和覆盖率提升，支持环境感知、CodeAgent 内嵌和 Skills 迭代。

产研助手承接需求、测试、DTS 和知识治理，通过多智能体和双轨记忆解决文档脱节和经验流失。

运维助手承接自动运维，通过 SSH 采集、LLM 推理、SSE 展示，实现采集、诊断、报告闭环。

### 3:40-4:30 效率与收益

从实践观察看，这不是几百行 Demo，而是核心应用约 2.7 万行、活跃工程资产约 7.1 万行的复杂工程。传统方式保守估算需要 60-95 人日，通过 AI 友好型工程流程后，投入压缩到约 23-39 人日，节省约 50%-60%。

单项看，新 API 端点从 1-2 天缩短到 2-4 小时，新业务接入从 3-5 天缩短到半天，依赖故障测试用例从 1-2 天缩短到 30 分钟，分布式系统根因分析从 2-8 小时缩短到 15-30 分钟。

更重要的是，质量也提升了。测试前置减少了理解偏差，白+黑减少了问题堆积，上下文工程让 AI 越用越准确。

### 4:30-4:50 收尾

总结一下，我们提交的不是一个孤立工具，而是一套 AI 友好型软件工程实践。它已经在 AIDP IAM / Gateway 复杂工程中验证，并且可以通过 IT 助手、产研助手、运维助手复制到黄区研发、测试和运维场景。
