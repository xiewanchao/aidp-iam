# AI 原生开发流程：从需求到生产的全链路人机协作范式

> **核心主张：** 软件开发的瓶颈从来不是"写代码"，而是需求理解的偏差、架构决策的反复、测试覆盖的盲区、以及跨会话的知识流失。本流程将 AI 嵌入每一个瓶颈节点，不是用 AI 替代开发者，而是让开发者的每一个决策都能被 AI 放大执行。
>
> **适用场景：** 中小型后端系统（微服务 / K8s 部署），团队规模 2–8 人，需要在有限人力下保证架构质量和测试覆盖。
>
> **实践基础：** 本流程提炼自 aidp-iam 项目（Kubernetes IAM + 网关鉴权栈）的真实开发过程，不是理论推演。

---

## 一、为什么需要这个流程

### 传统开发的四个系统性损耗

| 损耗点 | 传统方式 | 损耗来源 |
|---|---|---|
| 需求理解 | 文档评审 + 多轮澄清 | 隐含约束无法在文档里表达，靠经验猜 |
| 架构决策 | 会议讨论 + 个人经验 | 决策理由不留存，下次遇到同类问题重新讨论 |
| 测试覆盖 | 人工设计用例 | 依赖服务故障场景系统性遗漏，靠生产事故倒逼 |
| 知识传递 | 口口相传 + 文档 | 新成员上手慢，老成员离职带走隐性知识 |

### 本流程的解法

不是"用 AI 写更多代码"，而是**把 AI 放在每个损耗节点上**：

- 需求阶段：AI 主动追问隐含约束，把口头需求转化为可执行的结构化功能点
- 架构阶段：AI 生成选项 + 权衡，人工决策后 AI 将理由持久化，杜绝重复讨论
- 测试阶段：AI 从业务视角系统性推导测试场景，包括人工最容易遗漏的依赖故障场景
- 知识传递：三层持久化体系（项目约束 + 架构文档 + 跨会话记忆），AI 在任何新对话里都能恢复完整上下文

### 两阶段模型

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  阶段一：AI 主导构建期
  目标：以最快速度把骨架搭起来，AI 是主力，人工做关键决策
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  需求（自然语言）→ 结构化功能点 → 架构 + Schema + 接口契约
      → 分模块代码生成 → DT 测试用例 → 构建 / 部署脚本

  特征：AI 高频输出，人工高频决策，迭代以小时计

                ↓ 切换条件：核心路径可跑通 + 集成测试通过率 > 80%

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  阶段二：白 + 黑协作验收期
  目标：用真实业务场景打磨细节，人机分工到不同时段
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ☀️ 白天（人工主导）：部署 → 真实场景操作 → 记录问题日志
  🌙 夜间（AI 主导）：消化日志 → 根因分析 → 批量修复 → 回归测试
  ☀️ 次日：验证修复 → 发现新问题 → 继续记录

  特征：人工探索 AI 无法预见的边界，AI 系统性处理人工发现的问题
  循环直到验收通过 → 生产就绪版本
```

**为什么不一开始就白+黑？** 构建期的问题大多是"功能还没做"，人工测试发现的是空白，不是偏差。过早引入人工测试资源，测试人员大部分时间在等待，而不是在探索。切换时机是：问题从"功能缺失"变为"行为不符预期"。

## 二、需求阶段：把模糊变成可执行

### 2.1 AI 主导需求澄清

业务语言的需求天然包含大量隐含约束。"支持多租户"背后隐含数据隔离策略；"接入外部 IdP"背后隐含 token 验证链路；"资源级权限"背后隐含 ACL 数据模型。这些约束如果在需求阶段不澄清，会在架构阶段或代码阶段以 bug 的形式暴露，修复成本是需求阶段的 10 倍。

AI 收到需求后，不直接给方案，先追问边界：

```
必须澄清的五个维度：
1. 隔离粒度    — 数据库级 / schema 级 / 行级 / 无隔离
2. 鉴权位置    — 网关层 / 应用层 / 两者都有
3. 数据性质    — 静态配置 / 动态授权 / 混合
4. 外部依赖    — IdP 类型、消息队列、第三方 API 的 SLA
5. 性能基线    — 并发量、P99 延迟要求、数据规模
```

**输出格式：** 结构化功能点表格

| 原始需求 | 扩展功能点 | 隐含约束 | 验收标准 |
|---|---|---|---|
| 支持资源级权限 | 前缀匹配 ACL 查询 | 子资源继承父资源权限 | 给定 user + object，返回最长匹配的 ACL 记录 |
| 多租户隔离 | tenant_id 分层 schema | 跨租户查询必须被拦截 | 租户 A 的请求不能读取租户 B 的数据 |

### 2.2 技术选型：AI 给选项，人工拍板，决策永久留存

AI 输出 2–3 个选项 + 各自的权衡矩阵，不直接推荐。人工决策后，AI 将决策理由写入 `docs/architecture/question-and-answer.md`。

这份文档的价值在于**防止重复讨论**：AI 在后续任何对话里都会先读这份文档，不会在第 10 次对话里重新提出第 2 次对话里已被否定的方案。被否定的方案和否定理由同样重要——它们是团队已经走过的弯路，不应该再走第二次。

## 三、架构设计阶段：让设计决策可追溯

### 3.1 AI 生成初版架构

基于结构化需求，AI 输出三件套：

- **分层架构图**（ASCII / Mermaid）：组件职责边界，每个服务只做一件事
- **数据流时序图**：覆盖主路径 + 至少两个故障路径（依赖服务不可用时的降级行为）
- **组件交互矩阵**：哪些组件同步调用、哪些异步、哪些可以缓存

### 3.2 DB Schema 设计：隔离边界显式化

AI 生成 schema 时，隔离边界必须在表结构层面显式体现，不依赖应用层过滤：

```sql
-- 系统级（无 tenant_id）：全局配置，所有租户共享
-- apps, resource_patterns, resource_actions, path_rules

-- 租户级（有 tenant_id）：数据隔离，行级安全
-- resource_acl, api_keys, pending_acl
```

AI 在生成 schema 时主动标注：哪些表需要 `tenant_id` 索引、哪些需要复合索引、哪些查询会触发全表扫描。

### 3.3 接口契约锁定

AI 生成 OpenAPI 草稿后，接口契约一旦确认即锁定。后续代码生成以此为准，AI 不得自行修改接口签名——接口变更必须经过人工决策，并同步更新所有调用方。

## 四、代码生成阶段：约束感知，分模块推进

### 4.1 上下文注入：AI 生成前必须读取的四类信息

AI 生成代码不是从空白开始，而是在完整项目上下文里生成：

| 上下文来源 | 内容 | 作用 |
|---|---|---|
| `CLAUDE.md` | 架构约束、部署命令、环境限制 | 约束感知：不生成违反项目规范的代码 |
| `docs/architecture/` | 数据流、表结构、组件职责、故障模式 | 设计一致性：生成的代码符合已有架构 |
| `memory/` | 被否定的方案、调试陷阱、用户偏好 | 避坑：不重复已知的错误路径 |
| 现有代码 | 风格、库选择、命名约定 | 风格一致性：新代码和老代码看起来是同一个人写的 |

**约束感知生成的实际效果：** 项目里的 API 路径规范（`/api/v1` 是旧版残留，新路径用 `app-onboarding`）、K8s CRD 大小限制、镜像版本固定要求——这些约束写入 `CLAUDE.md` 后，AI 在每次生成时自动遵守，不需要用户每次提醒。

### 4.2 分模块推进：不一次性生成全部代码

按依赖顺序逐模块生成，每个模块生成后立即验证，不积累未验证的代码：

```
DB schema        → 验证：建表 SQL 可执行，索引符合查询模式
核心业务逻辑     → 验证：主路径端到端可跑通
边界处理         → 验证：异常输入、并发场景、依赖不可用
集成层           → 验证：网关路由、K8s 资源、端到端鉴权链路
```

每个模块验证通过后才进入下一个。这不是保守，而是让问题在最小范围内暴露，而不是在全部代码生成后面对一堆相互纠缠的 bug。

### 4.3 重构：行为不变，意图更清晰

重构时 AI 遵循严格的操作顺序：

```
1. 读取现有代码，理解当前设计意图（不假设，读代码）
2. 识别重构边界（接口签名不变，只改内部实现）
3. 生成重构后代码
4. 逐行对比差异，说明每处改动的原因
5. 运行现有测试，确认行为完全不变
```

**硬性规则：** 重构不引入新功能，新功能不顺带重构。两者混在一起提交，是 code review 最难发现问题的场景。

### 4.4 典型生成示例：前缀匹配 ACL 查询

这个设计让子资源（`/Details`、`/Password`）自动继承父资源权限，不需要为每个子路径单独写 ACL 记录：

```python
# 构造所有祖先前缀候选，从最长到最短（最长匹配优先）
parts = object_path.split("/")
candidates = ["/".join(parts[:i]) for i in range(len(parts), 0, -1)]

# 一次查询取最长匹配，避免 N+1
SELECT role_path, object_path FROM resource_acl
WHERE tenant_id = $1
  AND user_path = ANY($2)
  AND object_path = ANY($3)
ORDER BY LENGTH(object_path) DESC
LIMIT 1
```

AI 生成这段代码时，同时输出：为什么用 `ANY` 而不是 `IN`、为什么 `ORDER BY LENGTH` 而不是应用层排序、这个查询在什么数据规模下需要加索引。

## 五、DT 测试用例生成：业务视角，系统性覆盖

### 5.1 为什么 AI 生成的测试用例比人工更全面

人工设计测试用例有两个系统性盲区：
1. **依赖服务故障场景**：Keycloak 宕机、OPA 不可用、DB 连接超时——这些场景在正常开发环境里不会出现，人工容易遗漏，但生产环境里是高频故障源
2. **权限边界的组合爆炸**：多租户 × 多角色 × 多资源类型的组合，人工穷举成本极高

AI 从业务逻辑推导测试场景，不是从代码路径推导。代码路径视角容易产生"白盒测试"——测的是实现细节，而不是业务行为。

### 5.2 生成约束（硬性规则）

1. **三大场景必须覆盖**：正常流程 + 异常操作 + 依赖服务故障
2. **每个功能点标配**：1 条正向用例 + 至少 1 条异常/故障场景，异常用例不超过 5 条
3. **优先级排序**：用户高频操作 > 核心业务链路 > 高危边界场景
4. **黑盒视角**：站在不看代码的用户角度写，不暴露 API 名称和内部参数
5. **步骤与结果一一对应**：`用例_测试步骤` 和 `用例_预期结果` 数量必须相同
6. **故障用例命名**：`xxx服务在XXX时故障，导致xxx功能失败`
7. **预置条件通用项**：所有用例必须包含集群和基础服务正常的前提
8. **步骤可直接操作**：测试人员拿到用例不需要额外解释就能执行

### 5.3 输出格式：可直接导入测试管理工具

```csv
用例_名称,用例_编号,用例_预置条件,用例_测试步骤,用例_预期结果
普通用户查看自己信息成功,TC-001,"1、A800集群正常，模型服务、数据库、向量库服务集群正常；2、已有普通用户账号","1、使用普通用户账号登录系统；2、进入个人信息页面","1、登录成功，跳转至首页；2、正确显示当前用户的个人信息"
普通用户查看他人信息失败,TC-002,"1、A800集群正常，模型服务、数据库、向量库服务集群正常；2、已有两个不同的普通用户账号","1、使用用户A账号登录系统；2、尝试访问用户B的个人信息页面","1、登录成功；2、系统拒绝访问，提示无权限查看他人信息"
Keycloak在用户登录时故障导致Token获取失败,TC-003,"1、A800集群正常，模型服务、数据库、向量库服务集群正常；2、已有普通用户账号；3、Keycloak服务已停止","1、使用普通用户账号尝试登录系统","1、系统提示登录失败，无法获取认证令牌"
```

CSV 格式可直接导入测试管理工具，消除格式转换成本。代码刚写完，测试用例同步就绪，不需要等测试人员阅读代码再设计。

## 六、构建与部署脚本生成：安全内置，不是事后审查

### 6.1 Dockerfile：多阶段构建 + 最小权限

```dockerfile
# builder 阶段：安装依赖、编译，包含构建工具
# runtime 阶段：只复制产物，不含构建工具，镜像体积减少 60–80%

# AI 生成时强制检查：
# ✓ 非 root 用户运行（USER 指令）
# ✓ 固定基础镜像版本（不用 latest）
# ✓ 合并 RUN 指令（减少镜像层数）
# ✓ 不在镜像里存放密钥或配置（通过环境变量注入）
```

### 6.2 Helm Chart：生产就绪的默认配置

```
deploy/helm/<app-name>/
├── Chart.yaml           # 版本、依赖声明
├── values.yaml          # 默认值（不含密钥，可提交 Git）
├── values-prod.yaml     # 生产覆盖值（不提交 Git）
└── templates/
    ├── deployment.yaml
    ├── service.yaml
    ├── configmap.yaml
    ├── secret.yaml      # 引用 K8s Secret，不硬编码值
    ├── hpa.yaml         # 水平扩缩容
    └── _helpers.tpl
```

AI 生成 Chart 时主动检查四项生产就绪条件：镜像版本 tag、资源 requests/limits、健康检查探针、Secret 而非 ConfigMap 存放敏感配置。

### 6.3 CI/CD 流水线：从提交到生产的完整门控

```yaml
stages:
  - lint          # 代码风格，快速失败
  - test          # 单元 + 集成测试
  - build         # Docker 镜像构建
  - scan          # CVE 安全扫描
  - push          # 推送到镜像仓库
  - deploy-dev    # 自动部署到开发环境
  - smoke-test    # 自动冒烟测试
  - deploy-prod   # 人工审批后部署生产
```

### 6.4 脚本安全原则：生成时内置，不依赖 review 发现

AI 生成任何脚本时，以下四类问题在生成阶段就被拦截，不留到 code review：

| 风险 | 处理方式 |
|---|---|
| 硬编码密钥 | 替换为环境变量或 K8s Secret 引用 |
| 破坏性操作（`rm -rf`） | 加 `--dry-run` 模式或二次确认提示 |
| 生产数据库直接操作 | 加环境检测，非 prod 环境才允许执行 |
| 跳过 hook（`--no-verify`） | 拒绝生成，除非用户明确要求并说明原因 |

## 七、构建期验证闭环：根因分析，不是症状修复

### 7.1 快速迭代循环

```
代码修改 → rebuild.sh <component> → test.sh / curl → 分析日志 → 再修改
```

AI 在这个循环里的核心价值不是"改代码快"，而是**在改代码之前先找到根因**。

### 7.2 根因分析：沿调用链追溯，不停在表面现象

```
现象（HTTP 状态码 / 错误消息）
    ↓
调用链定位（哪个服务返回的错误）
    ↓
数据层验证（DB 数据是否符合预期）
    ↓
根因（代码逻辑 / 配置 / 初始化数据问题）
```

**实际案例：**
- 现象：`GET /AccessManager/Tenants/{id}/Users/{id}/Details` 返回 403
- 表面原因：OPA 拒绝了请求
- 追溯路径：OPA Rego 逻辑 → `path_rules` 数据 → DB init SQL → `WHERE NOT EXISTS` 语义
- 根因：DB 里的旧数据没有被新的 init SQL 覆盖，`WHERE NOT EXISTS` 导致新记录未插入
- 修复：补一条 `UPDATE` 语句处理存量数据，而不是改 OPA 逻辑

**关键实践：** 把完整的 JSON 报错体直接给 AI，比"访问被拒绝了"这类描述定位效率高 10 倍。

### 7.3 影响范围评估

每次修改前，AI 先评估影响范围，再动手：

> "修改 `permission_group_paths` 的 init SQL 只影响首次部署，已有集群需要手动 `UPDATE`，不影响其他表，不需要重启服务"

这个评估防止"改了一行 SQL 导致其他功能回归失败"的情况。

## 八、白 + 黑协作验收模式

> 这是阶段二的核心机制。进入条件：核心路径可跑通 + 集成测试通过率 > 80% + 可部署到真实环境。
> 未达到条件前，继续阶段一的 AI 主导快速迭代，不值得占用人工测试资源。

### 8.1 分工逻辑：人工做 AI 做不到的，AI 做人工不擅长的

| 维度 | 人工的不可替代性 | AI 的不可替代性 |
|---|---|---|
| 发现问题 | 真实业务直觉、使用习惯、审美判断 | 系统性覆盖、不遗漏、不疲劳 |
| 修复问题 | 判断"这是设计问题还是代码问题" | 批量根因分析、跨文件一致性修复 |
| 时间分配 | 白天工作时间（精力充沛，适合探索） | 夜间（无需休息，适合批量处理） |

### 8.2 白天：探索，不修复

```
部署最新版本到测试环境
    ↓
按真实业务场景操作（不按测试用例脚本，按实际使用习惯）
    ↓
记录问题日志（格式见 8.4 节）
    ↓
标注优先级（P0 阻断 / P1 影响体验 / P2 细节）
    ↓
下班前提交问题日志
```

**白天的纪律：** 不临时改代码、不在环境里打补丁、不跳过问题继续测。发现问题就记录，交给夜间 AI 处理。临时补丁会掩盖真实问题，让夜间 AI 修复错误的目标。

### 8.3 夜间：系统性消化，不引入新功能

```
读取全部问题日志（不跳过任何一条）
    ↓
分类：代码 bug / 配置问题 / 设计缺陷 / 环境问题
    ↓
按优先级排序（P0 → P1 → P2）
    ↓
逐条根因分析（沿调用链追溯）
    ↓
批量修复（相关问题合并处理，避免重复改同一文件）
    ↓
为每个修复生成对应的回归测试用例
    ↓
提交代码 + 更新日志状态（已修复 / 待确认 / 设计问题需讨论）
```

**夜间的纪律：** 不引入新功能、不顺带重构、不改接口签名。只处理白天日志里的问题。

### 8.4 问题日志格式

```markdown
## [日期] 测试问题记录

### P0 阻断问题
- [ ] **现象**：[操作步骤] → [实际结果] vs [预期结果]
  **环境**：[版本 / 账号类型 / 数据状态]
  **复现率**：必现 / 偶现（频率）

### P1 影响体验
- [ ] **现象**：...

### P2 细节问题
- [ ] **现象**：...
```

现象描述必须包含操作步骤和环境状态，不只是"点击后没反应"。AI 需要足够的上下文才能定位根因，而不是猜测。

### 8.5 次日交接摘要

次日白天开始前，AI 输出：

```
昨日修复：X 个（P0: N，P1: N，P2: N）
待人工确认：X 个（修复是否符合预期）
设计问题待决策：X 个（代码改不了，需要人工决定怎么做）
新增回归用例：X 条
```

人工先验证"待确认"项，再开始新一轮探索。

## 九、AI 记忆层：让知识不随对话结束而消失

### 9.1 三层持久化体系

传统 AI 工具的根本性缺陷：每次对话从零开始，用户需要重复解释背景，AI 会重新提出已被否定的方案，调试过的陷阱会再次踩到。

本流程通过三层持久化解决这个问题，而不是依赖更大的上下文窗口：

| 层级 | 载体 | 存储内容 | 特点 |
|---|---|---|---|
| 项目约束层 | `CLAUDE.md` | 架构规则、部署命令、环境约束 | 随代码库存在，所有 AI 会话自动加载 |
| 设计知识层 | `docs/architecture/` | 架构决策、数据流、故障模式、接入规范 | 与代码同步更新，是代码的"设计合同" |
| 隐性知识层 | `memory/` 系统 | 被否定的方案、调试陷阱、用户偏好 | 跨会话持久化，是 AI 的"避坑手册" |

三层结合，AI 在任何新对话里都能在 30 秒内恢复完整的项目上下文。

### 9.2 memory 文件结构

```markdown
---
name: short-kebab-case-slug
description: 一行摘要（用于判断相关性）
metadata:
  type: project | feedback | reference
---
核心内容

**Why:** 为什么有这条记忆（背景、事故、强偏好）
**How to apply:** 什么情况下应用这条记忆
```

### 9.3 三层文档的分工边界

- `docs/architecture/`：已确定的架构和设计，是代码的"设计合同"，不记录未确定的内容
- `memory/`：被否定的方案、调试陷阱、尚未落地的待确认需求，是 AI 的"避坑手册"
- 代码本身：唯一的真相来源，文档和记忆都是对代码的解释，不是替代

## 十、流程优势：与传统方式的量化对比

### 10.1 需求到可运行代码的时间

| 场景 | 传统方式 | 本流程 | 加速比 |
|---|---|---|---|
| 新 API 端点（含鉴权） | 1–2 天 | 2–4 小时 | 4–6x |
| 新业务应用接入（含路由 + ACL） | 3–5 天 | 半天 | 6–10x |
| 依赖服务故障测试用例设计 | 1–2 天（经常遗漏） | 30 分钟（系统性覆盖） | 4–8x |
| 根因分析（分布式系统） | 2–8 小时 | 15–30 分钟 | 8–16x |

*以上数据基于 aidp-iam 项目实际开发过程的观察，不同项目会有差异。*

### 10.2 质量维度的提升

| 质量维度 | 传统方式的问题 | 本流程的改进 |
|---|---|---|
| 架构一致性 | 新代码风格和老代码不一致，靠 review 发现 | 上下文注入保证生成代码匹配现有风格 |
| 安全性 | 硬编码密钥、权限过宽靠 review 发现 | 生成时内置安全检查，不依赖 review |
| 测试覆盖 | 故障场景系统性遗漏 | AI 强制覆盖三大场景，包括依赖故障 |
| 知识留存 | 依赖个人记忆和文档，人员流动导致知识流失 | 三层持久化，知识和代码库绑定 |

### 10.3 人机协作的本质分工

这个流程不是"用 AI 替代开发者"，而是**让人和 AI 各做自己最擅长的事**：

**人工不可替代的：**
- 业务价值判断（这个功能值不值得做）
- 架构权衡决策（在多个合理方案里选一个）
- 真实业务场景的探索性测试（发现 AI 无法预见的边界）
- 设计问题的识别（这是代码 bug 还是设计缺陷）

**AI 不可替代的：**
- 隐含约束的系统性推导
- 跨文件的一致性保证
- 依赖故障场景的系统性覆盖
- 批量根因分析（不疲劳、不遗漏）
- 跨会话的知识持久化

## 十一、可扩展性：从单项目到通用范式

### 11.1 新业务应用接入

新应用接入时，AI 读取 `docs/onboarding/app-integration-guide.md`，生成符合项目规范的全套资产：
- `manifest.json`（资源模式、路径规则、默认 ACL）
- 网关路由配置（HTTPRoute + SecurityPolicy）
- 对应的 DT 测试用例（覆盖新应用的权限场景）

接入成本从天级降到小时级，且生成的配置格式与现有应用完全一致。

### 11.2 新技术组件引入

引入新开源组件时，AI 生成两份文档：
- `*_first-introduction-review.md`：功能匹配度、许可证、社区活跃度、安全漏洞历史
- `*_selection-evaluation.md`：与备选方案的对比和最终选择理由

后续 AI 在建议替换某个组件时会先读这两份文档，了解当初为什么选它，不会提出已被否定的替代方案。

### 11.3 迁移到其他项目

本流程的核心机制（三层持久化 + 约束感知生成 + 白+黑验收）与具体技术栈无关。迁移到新项目时，只需要：

1. 建立新项目的 `CLAUDE.md`（项目约束）
2. 建立 `docs/architecture/` 目录（设计知识）
3. 初始化 `memory/` 系统（隐性知识）

这三个文件建立后，AI 就能在新项目里以同样的方式工作。

### 11.4 流程本身的自我演进

本 SKILL 是活文档，随项目实践持续更新：
- 发现新的 AI 生成陷阱 → 更新 `memory/` + 本 SKILL 的注意事项
- 发现新的高效模式 → 更新本 SKILL 的对应阶段
- 架构演进 → 更新 `docs/architecture/` + 本 SKILL 的架构设计章节

流程的演进本身也由 AI 辅助完成——每次发现流程改进点，AI 同步更新文档，保证流程描述和实际执行方式始终一致。
